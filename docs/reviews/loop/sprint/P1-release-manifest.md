## 4. Implementation

### 4.1 `scripts/release_manifest.py` (`make release-manifest`)

Offline; runs under `$(PY)`; never runs a gate; imports `erev_engine.ENGINE_VERSION`, `erev_api.db.migration_ops.code_head` and `erev_api.controls.registry.load_controls` lazily. Options `--root`, `--reports-dir` (default `<root>/.run/reports`), `--out` (default `<root>/release-manifest.json`), `--controls`, `--command`, `--strict`; the make variable `STRICT=1` adds `--strict`, and the script also honours `STRICT=1` in its environment.

- Step (1): `build_sha` = `git rev-parse HEAD` or `"nogit"` (DG-MK-00g); `worktree_dirty` = `git status --porcelain` non-empty; `schema_revision` = `code_head()` (the single head; raises on several); `created_at` UTC with microseconds.
- Step (2): `gate_result(path, build)` decides in the REL-02 order: absent → `NOT_RUN`; report not a JSON object → `NOT_RUN` (digest still recorded); `build_sha` ≠ current → `NOT_RUN`; `exit_code` not an integer → `NOT_RUN` (a report proves neither outcome; judgement, not in the text); `exit_code` ≠ 0 → `FAIL`; `worktree_dirty` not `False` → `NOT_RUN` (a report lacking the DG-MK-00g field is treated as dirty; judgement); else `PASS`. `command` and `finished_at` are copied from the report, `output_sha256` is the SHA-256 of the report file bytes.
- Step (3): `<base>` = `git describe --tags --abbrev=0 --match "v*"`, else the empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904` inside a repository, else no diff (`nogit`). Paths from `git diff --name-only <base>..HEAD`. Globs: `**` spans directories (`**/` zero or more, trailing `/**` everything below), `*` and `?` stay within one segment, everything else literal, whole-path match (`glob_to_regex`). Tags sorted. No `v*` tag exists in this repository, so the base is the empty tree and the whole tree counts as changed: 47 of 49 controls are tagged on `c40b69e` (CTL-045 and CTL-048 have globs matching no committed path).
- Step (4): SHA-256 of `backend/uv.lock` and `frontend/package-lock.json`, null when absent.
- Step (5): `images` from `.run/reports/docker-build/report.json` only when that report's `build_sha` is the current one (judgement: a report of another build describes other images; a stale report yields nulls, never a copied id); `audit_deps` `{result, output_sha256}` with `result` by the step (2) rules and `output_sha256` the report's own field (DG-MK-audit-deps step 4) or, without it, the report file's digest; null without a report.
- Step (6): manifest written with `json.dumps(sort_keys=True, indent=2) + "\n"`; `.run/reports/release-manifest/report.json` in the DG-MK-00g shape with `counts {gates: {PASS, FAIL, NOT_RUN}, control_impact_tags, changed_paths}`, `failures` (`{stage: "strict", exit_code: 1, gates: [...], worktree_dirty}` under `--strict`), `manifest`, `impact_base`, `strict`. Output `release-manifest: <path> (build <12>, gates PASS n FAIL n NOT_RUN n, control impact tags n)` then `OK release-manifest` or `FAIL release-manifest: STRICT: <gate> <result>, …[, worktree dirty]`.

The manifest is written before the strict verdict, so a red strict run still leaves the evidence file (the report says `exit_code 1`).

### 4.2 `scripts/docker_build.sh` (`make docker-build`)

DG-MK-docker-build steps with one addition. (1) `docker info` fails → `{"result": "skipped-no-daemon", …}` report, `SUPERVISOR VERIFICATION NEEDED: Docker daemon unavailable`, `OK docker-build`, exit 0. (1a, addition) `release-manifest.json` absent → `FAIL docker-build: release-manifest.json is missing; run make release-manifest`; its `build_sha` ≠ HEAD → `FAIL docker-build: release-manifest.json names build <12> but HEAD is <12>; run make release-manifest`; both before any build, both recorded as `failures[0].stage = "manifest"`. (2) `docker build [--no-cache] -f deploy/docker/<image>.Dockerfile -t erev-<image>:<12> .` from the repository root, output to `.run/reports/docker-build/<image>.log`, the last 20 lines echoed on failure. (3) `docker image inspect --format '{{.Id}}'` per image; report `images {tag, digest}`, `manifest_build_sha`, `counts {images, no_cache}`, `result` `built`. No `push`, no `login`; the script text does not even contain those two invocations (DEP-5 static rule). The Makefile target prints `SUPERVISOR TARGET docker-build (D-48a)` first (DG-MK-00h), then `$(REQUIRE_SETUP)`, then `make release-manifest`, then the script with `NO_CACHE` and the recorded command. Test-only overrides `EREV_DOCKER_BIN`, `EREV_DOCKER_BUILD_ROOT` (and `EREV_RUN_DIR` as in `proc.sh`) let the contract test run against a stand-in binary and a scratch root.

Consequence for compose (§8 Q-3): `docker compose … build` now needs `release-manifest.json` present in the context, so `make release-manifest` precedes a compose build (DG-RUN-16, runbook).

### 4.4 `erev_api.controls.release`

`release_facts` and `stamp_release` take `manifest_path: Path | None = None` and `build_sha: Callable[[], str] | None = None` and resolve `MANIFEST_PATH` and `git_build_sha` at call time (before: bound as defaults at definition time, so a test could not point a production-mode app at another file). Behaviour with the defaults is unchanged. An unreadable manifest (`OSError`, `UnicodeDecodeError`) is reported as `ReleaseManifestError("release-manifest.json cannot be read")` instead of escaping as an I/O error. The validation of a malformed or mismatched manifest (`facts_from_manifest`: not an object, another engine version, another schema revision, empty `build_sha`, malformed `control_impact_tags` or `gate_results`) existed and is unchanged; `build_sha` versus image content is not defined by the spec and was not added (the build script's HEAD check is the build-time counterpart).
