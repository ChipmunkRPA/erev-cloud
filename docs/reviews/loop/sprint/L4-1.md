### Spec questions

- **L4-1-Q-1.** `MANUAL_EVENT` before CTR-6.
  - `POST /events/{id}/request-void` must answer `{event_submission_id, approval_request_id}`, and `approvals.submit` needs a subject spec. CTR-6 builds that spec, and it is deferred in V-ABC.
  - [J] The minimal spec: permission `event.approve`, not revenue-affecting, content = contract and stored events, no entity reference (the approval read cannot show an entity yet, XR-12). On approval SYSTEM appends the events for the preparer, the submission goes SUBMITTED → APPROVED → APPLIED with `applied_event_ids`, and the group is only marked dirty. Rejection gives REJECTED; void and withdraw give VOIDED.
  - A stored item carries `supersedes_event_id` beside the API-S-EventAppend members.
  - Request: confirm, or move the void approval to CTR-6 and rule the response until then.
- **L4-1-Q-2.** Exception titles.
  - SCREENS §13.5 fixes nine titles; other codes use the first clause of their PRD IMP message, but those clauses carry placeholders ("No approved SSP for <SKU / stratification / version>").
  - [J] `finding_title` keeps the nine and titles other codes from the code words in sentence case, keeping SSP, VC, FX, POB, EAC, SFC, DQ, AI, GL and RPO ("SSP key not found").
  - `erev_api.findings.CODES` does not exist yet, so a code is checked against the §15.4 format only.
  - Request: name the catalogue and its owner.
- **L4-1-Q-3.** Refused computations. [J]
  - A QUARANTINED or FAILED computation leaves `head_computation_id` and `latest_computation_id` on the latest SUCCEEDED computation, and the group stays dirty.
  - FAILED raises `ENGINE_INVARIANT_VIOLATION`, because §15.4 has no code for a programming error.
  - Unit of work B runs in a savepoint of the command's transaction, so the events and the refused computation commit together; a deferred DB-17 violation at commit still fails the command.
  - Request: confirm.
- **L4-1-Q-4.** What `POST /contracts/{id}/events` records. [J]
  - The measure, billing, credit, payment, cost, pre-standard revenue, memo and flag types. Types with their own commands answer 422 rule `API-R-30`.
  - Every event appends directly: manual-event routing waits for CTR-6. `is_manual` is true for a signed-in person, false for API clients (PRD ACT-10).
  - `evidence_file_ids` and `comment` are accepted and audited, not enforced (REQ-DAT-014 is CTR-6).
  - `INVOICE_STATUS_UPDATE_MISMATCH` is not checked, because it is not in the item's validation list.
  - Request: confirm the recorded types.
- **L4-1-Q-5.** Event preview. [J]
  - `POST …/events/preview` validates as an append, then defers `CONTRACT_COMPUTE` in mode `PREVIEW`. The job computes the group in `DRY_RUN` with the events pending and stores API-S-ImpactSummary in `result.summary`. `JobResultOut` became an open object, so other jobs' results are unchanged.
  - Summary choices: catch-up is the change in cumulative revenue per obligation, with `treatment` null; `rpo_date` is the latest effective date of the events; balances are empty and progress null; `journal_lines` total the dry run's intents in the contract currency; before figures come from the latest primary-book version.
  - Request: confirm, and name the E-14 kind if a preview needs its own.
- **L4-1-Q-6.** Event submissions. 04 defines no API-S schema. [J] `EventSubmissionOut` is the T-CON-24 columns with `created_by` as API-S-Actor. The list takes `contract` and `status`, sorted by `-id` or `created_at`. Request: confirm.
- **L4-1-Q-7.** `GET /schedule-lines`. [J]
  - Lines of each group's latest version in the book recorded by `known_at`.
  - `from_period` and `to_period` bound by start date within each line's calendar; `obligation` takes a key or id and `entity` a code or id.
  - Without `contract` every visible contract is listed; the default sort is `period_end_date`.
  - Request: confirm.
- **L4-1-Q-8.** `LATE_EVENT` findings in the rc engine.
  - Stage 14 places a late posting with `reason_code = LATE_EVENT`, but nothing calls stage 08 `late_events`, so the S08-R-10 findings never reach `OutputBundle.diagnostics`.
  - [J] After a new computation, the platform raises `LATE_EVENT` (WARNING, source ENGINE) for each newly included event whose effective period is not postable, through DG-KRN-TIME-04 `posting_period`. It uses the IMP-39 message and the origin period, under the key `ENGINE:LATE_EVENT:<event id>` that the diagnostic path uses, so an engine finding later counts on the same item. The out-of-order clause of S08-R-10 waits for the engine.
  - Request: name the engine item that publishes the stage 08 findings.
