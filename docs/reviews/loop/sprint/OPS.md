## 10. Lock budget: PRODUCT DEFECT (deployment), fixed

Neither the compose server nor the Cloud SQL flags set `max_locks_per_transaction`, so every shipped shape ran on PostgreSQL's default of 64. Measured on the compose PostgreSQL 17 at revision 0072 (181 partitions of `audit_event`, `schedule_line` and `subledger_line` with 5, 4 and 5 indexes each; 5,044 relations in the database):

| Measurement | Figure |
|---|---|
| One statement on `audit_event` / `schedule_line` / `subledger_line` that names no partition value; all three in one transaction | 1,092 / 910 / 1,092 relation locks held to the end of the transaction; 3,094. Equal to the catalogue formula `1 + parent indexes + partitions × (1 + indexes per partition)` |
| `schedule_line` for one month by literal; `subledger_line` for twelve months | 10; 78 |
| One month by parameter under a generic plan: first execution; cached | 910; 182 |
| Demo seed, one backend: largest holding | 2,257 `pg_locks` rows (`schedule_line` 931, `subledger_line` 1,092, other 230). Half of the 2,109 samples held 400 to 999 |
| Audit-chain verification of 8 workspaces by one worker | 1,134 per backend; 3,343 rows at once with three running |
| `erev migrate` on an empty database, at the end of each revision's transaction | 0006: 2,035 distinct lock objects; 0039: 3,103; 0040: 4,854 (6,543 rows); every other revision 219 or fewer |
| Server at the defaults (64 × 100 = 6,400 nominal slots): sessions that each hold the 3,094 footprint | Nine admitted; the tenth answered SQLSTATE 53200 `out of shared memory` |
| Server started with 4096: the same | All 80 admitted (247,602 `pg_locks` rows), no refusal |
| `shared_memory_size` PostgreSQL 17 computes, 64 against 4096 | 143 MB against 327 MB at 100 connections; 168 MB against 1,136 MB at 600 |

Rule (05 §2.7): `max_locks_per_transaction × (max_connections + max_prepared_transactions) ≥ ⌊0.8 × max_connections⌋ × partition lock footprint + relations`. It needs 2,526 at 100 connections and 2,484 at 600. Set: `deploy/compose.yaml` starts `postgres` with `max_locks_per_transaction=4096`; Terraform variable `db_max_locks_per_transaction` (default 4096, validation `>= 3072`) sets the Cloud SQL flag, with `output db_lock_budget`. Checked: `erev doctor` production check `lock-budget` (`controls/doctor.py`), over the three settings and the two catalogue counts read as `erev_app`; it names the smallest sufficient setting and fails closed without an observation or without a partitioned table. In the api container of the compose stack it prints `OK lock-budget: 409600 lock slots (max_locks_per_transaction 4096) cover 80 sessions × 3094 partition locks + 5044 relations = 252564 (05 §2.7)`; against the same server before its restart the collector gave `FAIL lock-budget: … gives 6400 lock slots; … need 252564 (05 §2.7): set max_locks_per_transaction to at least 2526 and restart PostgreSQL`. The runbook's "PostgreSQL lock table" states the requirement for a self-hosted server (restart only) and what 53200 means. Tests: `tests/unit/test_doctor_production_checks.py` (the predicate, the collector, the wiring), `tests/unit/deploy/test_lock_budget_settings.py` (the shipped settings against the rule and the documents), `tests/pg/test_lock_budget.py` (against a migrated database, where the catalogue formula is shown to be what one statement locks), `tests/unit/docs/test_guides.py` (the runbook). Not verified: the flag on a live Cloud SQL instance (no cloud call; `make tf-validate` passes).

## 17. OPS-SBX-KEY-1: the design of record (ruling R-108 (4))

**Ruling.** The first release offers no sandbox copies on the hosted shape: a hosted sandbox copy fails closed, as the runbook's "Sandbox copies on a hosted deployment" says, and that is a known limitation of the hosted shape. The design below is the design of record for the release that offers them. It is built when a hosted deployment is commissioned and its grant can be verified on a live project; until then none of it is in the tree, because a grant without the code that uses it is a dormant privilege.

**Design.** The worker creates and initialises the audit key of a sandbox tenant under a sandbox-only sub-prefix of the tenant audit keys' prefix (`<prefix>audit-hmac-sbx-`). The readers' existing condition (`<prefix>audit-hmac-`) already covers the sub-prefix; a tenant id is a UUID, so no production tenant's secret name begins with `sbx-`.

The Terraform text for `deploy/terraform/gcp/main.tf`, validated with `make tf-validate` on a tree that held it (`Success! The configuration is valid.`, `OK tf-validate`) and removed again. The first line belongs to the `locals` block that holds `tenant_audit_hmac_secret_prefix`:

```hcl
  # OPS-SBX-KEY-1 (proposal): a sandbox tenant's audit key lives under its own sub-prefix, so the
  # worker's initialiser grant can name sandboxes and nothing else. A tenant id is a UUID, so no
  # production tenant's secret name starts with it; the readers' prefix above still covers it.
  sandbox_audit_hmac_secret_prefix = "${local.tenant_audit_hmac_secret_prefix}sbx-"

# OPS-SBX-KEY-1 (proposal): the worker creates and initialises the audit key of a SANDBOX tenant
# during a sandbox load (05 SBX-04). Creation cannot be narrowed by name (it is checked against the
# project), so the worker holds the create-only role as the provisioning identity does; get, add
# and read-back are bound under the sandbox sub-prefix only, so no production tenant's secret can
# be appended to by the worker.
resource "google_project_iam_member" "worker_sandbox_secret_creator" {
  project = var.project_id
  role    = google_project_iam_custom_role.tenant_secret_creator.id
  member  = "serviceAccount:${google_service_account.worker.email}"
}

resource "google_project_iam_member" "worker_sandbox_secret_initializer" {
  project = var.project_id
  role    = google_project_iam_custom_role.tenant_secret_initializer.id
  member  = "serviceAccount:${google_service_account.worker.email}"

  condition {
    title       = "erev-sandbox-audit-hmac-secrets-initialise"
    description = "Only sandbox tenants' audit HMAC secrets (${local.sandbox_audit_hmac_secret_prefix}<tenant id>)."
    expression  = "resource.name.startsWith(\"projects/${local.project_number}/secrets/${local.sandbox_audit_hmac_secret_prefix}\")"
  }
}
```

**What the grant gives the worker.** Creation of empty secrets of any name in the project (the create permission is checked against the project and cannot be narrowed by name, as `main.tf` notes for the provisioning identity; not verified on a live project), and get, add-version and read-back on sandbox tenants' keys only. It already reads every tenant key, so confidentiality does not move, and it can append to no production tenant's secret. Since 05 KEY-09 rev 1.47 adapter credentials live in a workspace's own namespace (`<prefix>tenant-<tenant id>-<name>`): the create permission lets the worker occupy a name there before the operator creates it, with its own replication and expiry settings and never with a value, because it can add no version outside the sandbox sub-prefix.

**What it needs in code** (not built): the secret name, and so the key id, of a sandbox tenant carries the sub-prefix (04 T-PLT-01, 05 KEY-05), and the Terraform secret-access matrix test gains the worker's row.

**Not taken.** Handing key creation to the `erev-tenant-provision` job: the worker would need to run a job whose command is `erev tenant create` with overrides, and could then create whole workspaces under the provisioning identity.

**Likewise not granted in the first release (item OPS-IAM-ADAPTER-SECRETS-1).** No identity reads the adapter namespace `<prefix>tenant-<tenant id>-…`: the first release ships no live adapter, so a hosted adapter connection fails closed (the connection test records a failure, the webhook receiver answers 401). The binding for the release that ships one is `roles/secretmanager.secretAccessor` for the api and the worker under the condition that the name starts with `<prefix>tenant-`, with two rows of the secret-access matrix test.
