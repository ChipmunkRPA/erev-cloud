### Spec questions

- **L1-1-Q-1.** 04 §16 defines no calendar schema. RFD-1 returns `CalendarOut`: the T-REF-04 columns plus `created_at`, `updated_at` and `row_version`. `generate-year` returns `{calendar_id, fiscal_year, inserted_count, periods[]}`, with the members of API-S-Period `period` (§16.8). `POST /calendars` answers 201 with an `ETag` but no `Location`, because API-R-18 has no `GET /calendars/{id}` (DG-CMD-12). Request: confirm this shape, or define API-S-Calendar.
- **L1-1-Q-2.** E-50 `W5253` names the 52/53-week year rule only; 04 T-REF-04, BS3-D-16 and REQ-REF-003 give no period layout. RFD-1 generates the 4-4-5 layout with the extra week in period 12, which meets the acceptance ("fiscal-year boundaries equal those of the P445 calendar"). The alternative is month-anchored periods. Request: rule on the W5253 period layout.
- **L1-1-Q-3.** DB-05 also freezes period rows referenced by a `subledger_line` or a non-`future` `period_state`, and `fiscal_calendar` pattern fields once any of the calendar's periods is referenced. At RFD-1 no referencing table exists, so neither freeze could ever fire. By analogy with DG-MIG-03, revision 0027 creates only the contiguity trigger. RFD-2, which creates `period_state` and names `test_db_05_period_frozen_when_state_not_future`, adds the period freeze and the calendar pattern freeze; the item that creates `subledger_line` adds that leg. Request: confirm the split.
- **L1-1-Q-4.** API-R-18 grants the calendar commands to "any of `masterdata.maintain`, `settings.manage`", but `require(permission)` takes a single code. The routes therefore use `command(per_subject=True)`, and the handler authorises through `erev_api.domain.platform.attachments.authorize`: any of the codes, a `DENIED` audit event, and the MFA rule applied only when every held code requires MFA. This follows API-R-12 and SPEC-Q-157. As a result the operations carry no `x-erev-permission` in the OpenAPI document. Request: confirm, or add a multi-code guard to the kernel.
- **L1-1-Q-5.** Decisions taken, listed for review:
  - (a) `MONTHLY` refuses `week_end_day` and `year_end_anchor` with 422 (`T-REF-04`). The table adds `ck_fiscal_calendar__week_end_day` (1 to 7), `__year_end_anchor` and `__week_fields` (a week-based pattern needs both).
  - (b) A fiscal year is named by the calendar year of its end month, January starts included. Under the nearest-weekday anchor, a week-based FY Y may end up to three days into January of Y+1.
  - (c) `generate-year` accepts `fiscal_year` from 1900 to 2999.
  - (d) Audit actions are `fiscal_calendar.create` and one `period.generate` per inserted period (AUD-CMD "per affected object"); a repeated generation writes no event.

### Spec questions

- **L1-1-Q-26.** 04 §16 defines no currency or FX schema. RFD-3 returns the table columns plus `created_at`, `updated_at` and `row_version`.
  - `TenantCurrencyOut` adds the currency's name, minor unit and `is_reporting_currency`.
  - A version adds its set's code and rate type and `pending_approval_request_id`. Lists omit the rates; the detail and every command response include them.

  - Request: confirm, or define API-S-Currency, API-S-FxRateSet, API-S-FxRateSetVersion and API-S-FxRate.
- **L1-1-Q-27.** API-C-06 and DG-KRN-MONEY-06 require `erev.fx_rate` strings with trailing zeros trimmed. The RFD-3 acceptance requires `"1.105000000000"` and `"0.781250000000"`. RFD-3 follows the acceptance and returns the stored twelve-place string. Request: rule which governs; trimming would be a one-line change in `fx.format_rate`.
- **L1-1-Q-28.** DB-04 names an overlap check "against rows … with status PUBLISHED (APPROVED for SSP and FX versions)". T-REF-11 resolves from "the highest APPROVED `version_no`", and `test_highest_approved_version_wins` needs two APPROVED versions covering September 2026.
  - Revision 0030 attaches `erev.tg_config_version()` unchanged. Its overlap check applies only to PUBLISHED, which an FX version never reaches, so APPROVED versions may overlap.
  - Approval supersedes nothing, and the E-12 pair APPROVED → SUPERSEDED is not among the function's pairs.
  - Request: rule whether FX approval supersedes earlier versions, and whether overlapping APPROVED versions are refused.
- **L1-1-Q-29.** Resolution semantics:
  - Per set, the highest APPROVED version whose coverage contains the date answers for that date, whether or not it holds the pair (literal T-REF-11).
  - Across sets of one rate type, the most recently approved version wins (`published_at`, then id).
  - Request: rule on a pair-level fallback to earlier versions, and on precedence between sets (or add a set filter to `GET /fx-rates`).
- **L1-1-Q-30.** T-REF-12 derives inverses "at publication", but DB-04 `tg_config_child` refuses child rows once the version leaves DRAFT or TESTED.
  - Submission therefore inserts the inverse of every entered pair without an entered inverse while the version is still DRAFT. Their hash is covered by the approval, and they take effect at approval.
  - `rate_count` counts entered and derived rows.
  - Triangulated cross rates (PRD §2.5 world "GBP→EUR … derive through USD") are not derived, because no pivot currency is named.
  - Request: confirm submission-time derivation; rule on triangulation and its pivot.
- **L1-1-Q-31.** `missing-fx-rate` details:

  - Request: confirm.

- **L1-1-Q-38.** 04 §16 defines no customer schema. RFD-8 returns the T-REF-18 and T-REF-19 columns plus `created_at`, `updated_at` and `row_version`.
  - `CustomerOut` adds `related_party_group` (API-S-Ref or null), because the SCREENS §9.4 grid column "Related-party group" shows the group's code and name.
  - `RelatedPartyGroupOut` adds `member_count` (§16.14).
  - `POST /customers` answers 201 with `Location` and `ETag`. `POST /related-party-groups` answers 201 with `ETag` but no `Location`, because API-R-22 has no `GET /related-party-groups/{id}` (DG-CMD-12).
  - Request: confirm, or define API-S-Customer and API-S-RelatedPartyGroup.
- **L1-1-Q-39.** `member_count` counts every customer of the group, active or not, because a deactivated customer remains a related party for disclosure. Request: confirm, or count active customers only.
- **L1-1-Q-40.** `source_system` and `external_id`:
  - Both are members of `POST /customers`, because the acceptance creates a NetSuite customer through the API. Without `source_system`, the principal kind decides (`API` or `MANUAL_UI`, as L1-1-Q-8). `create_customer(..., source_system=…)` lets imports (for example `LEGACY_TEMPLATE_V1`) name their channel, and takes precedence.
  - Neither is a member of PATCH (422), following SCREENS §9.5 "Source and External id read-only".
  - The external id is stored exactly as sent, because adapters match it literally; a blank one returns 422.
  - Request: confirm; rule whether a manual customer may receive an external id later.
- **L1-1-Q-41.** SCREENS §9.5 makes the customer code read-only "after the first contract references the customer". No contract table exists at RFD-8, so PATCH changes a code freely (uniqueness checked). Group codes also change. Request: assign the code freeze to the item that creates `contract` (a command check or a trigger), and confirm that group codes are editable.
- **L1-1-Q-42.** List decisions:
  - Customers sort by `name` by default and groups by `code`, where API-C-09 names `id` descending; this follows the lane precedent of the grid's natural key (L1-1-Q-12).
  - `q` searches code, name and external id for customers, and code and name for groups.
  - The group list takes sort keys `code`, `name`, `updated_at` and `id`, and no filters.
  - `external_id` is exact-match; `source_system` accepts the E-38 literals.
  - Request: confirm.
- **L1-1-Q-43.** Validation decisions:
  - A parent must exist and must not close a loop; a group must exist.
  - `country_code` is ISO 3166-1 alpha-2 in capitals, in the command and through `ck_customer__country_code` (as for `legal_entity`, L1-1-Q-24).
  - `credit_grade`, `segment` and `description` are free text with surrounding spaces removed; a blank value is null.
  - A concurrent duplicate reaching a unique key surfaces as 500, because §15.2 maps no 23505 (as L1-1-Q-11).
  - Request: confirm; rule whether credit grade and segment take a vocabulary.
- **L1-1-Q-44.** Audit action names: `customer.create`, `customer.update`, `related_party_group.create`, `related_party_group.update`. Request: confirm.
- **L1-1-Q-45.** T-REF-17 takes `customer` dimension values from `customer.code`. RFD-8 leaves `GET /dimensions/customer/values` empty, because API-R-21 belongs to RFD-6 and no RFD-8 text changes it. Request: rule together with L1-1-Q-10.
- **L1-1-Q-46.** `customers.related_customer_ids` returns the other members of the group in code order, active or not, for REQ-CON-010. Request: confirm whether combination detection should consider inactive customers.
