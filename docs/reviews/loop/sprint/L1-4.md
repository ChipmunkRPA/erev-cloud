### Spec questions

- **L1-4-Q-1 (RFD-4).** The acceptance creates `POST /rule-sets {code, kind}` with no name, yet T-REF-24 `name` is NOT NULL. [J] `name` is optional and defaults to the code.
- **L1-4-Q-2 (RFD-4).** API-R-25 does not state the status of an upsert that replaces a rule. [J] 201 when the rule is created (with the created rule) and 200 when it is replaced. The route chooses the status from a read before the command transaction, so a concurrent upsert can only change the status code.
- **L1-4-Q-3 (RFD-4).** 04 §16 defines no schema for rule sets, rule set versions, rules or configuration test cases. [J] Fields follow T-REF-24 to T-REF-27 and SC-V, with the §16.14 list additions. Further judgements:
  - An example case of a rule set version expects at least one of `matched`, `rule_key` and `outputs`.
  - One version of a set is open (DRAFT, TESTED, SUBMITTED or APPROVED) at a time, as SPEC-Q-184 decided for SoD rule versions.
  - Routed steps are limited to 10.
- **L1-4-Q-4 (RFD-5).** E-12 and DB-04 (`CONFIG_STATUS_PAIRS`) have no TESTED → DRAFT pair, while SCREENS §11.0 and API-C-13 say that editing a TESTED version returns it to DRAFT. This lane adds no Alembic revision, so [J]:
  - An edit keeps TESTED.
  - `/submit` refuses with 409 `invalid-transition`, rule REQ-POL-003, when the content hash differs from the one `/test` recorded, when a case has not passed, or when the lint is not PASS.
  - `/test` on a TESTED version records a new hash; DB-04 allows this while TESTED, but SC-V says the hash "never changes afterwards".
  - T-REF-25 has no `test_evidence` column, so `test_evidence` is derived from the T-REF-27 `last_result` and `last_run_at` of the cases.
  - TESTED needs at least one example case and a lint status of PASS (the T-REF-25 `lint_result` note).
  - Supervisor: add TESTED>DRAFT to E-12 and DB-04, or confirm this reading.
- **L1-4-Q-5 (RFD-5).** The acceptance reads "version 1 `effective_to` to 2026-09-30". SC-V ranges are half-open `[effective_from, effective_to)` (DB-04 `tstzrange`, D-80), so the stored `effective_to` is 2026-10-01T00:00:00Z, which equals version 2's `effective_from`; the last day version 1 is in force is 2026-09-30. `test_publish_supersedes_prior_version` asserts both.
- **L1-4-Q-6 (RFD-5).** The acceptance facts `product` and `region` are shorthand; the tests use the `erev_engine.rules.FIELDS` names `product.code` and `contract.region`.
  - [J] The `/evaluate` body is `{facts, version_id?, at?}`, so authors can evaluate drafts. Without `version_id` it evaluates the PUBLISHED version in force, as routing does.
  - `/evaluate` is a POST, so DG-ARC-04 requires `command(...)` and an `Idempotency-Key`; it writes nothing.
- **L1-4-Q-7 (RFD-5).** API-S-SimulationSummary has no text member, yet BR-POL-01 says the report "states 'No contracts affected'". [J] The summary gains a `statement` member, and the report is stored with purpose `REPORT_OUTPUT`, because E-68 has no simulation purpose.
- **L1-4-Q-8 (RFD-5).** `approvals/routing.py` `_matched` reads PUBLISHED versions only. After a version with a future `effective_from` is published, the superseded version routes nothing until that date, and requests take the fallback step. For SoD rules, D-80 counts a SUPERSEDED version for instants in `[published_at, effective_to)`. The suggested fix is for `_matched` to also read SUPERSEDED versions within their range; I did not change it because the file is outside the lane scope.

### Judgements and deviations

- **REQ-POL-003 author check.** `lifecycle.approve` refuses approval by the version's author (`created_by`), even when the author did not submit: 403 `self-approval`, and the decision rolls back. `published_by` is null for an `AUTO_APPROVE` publication.
- **Lint is conservative.** Two rules tie when their specificity and priority are equal and every field both name has a value meeting both rules' conditions. Collection facts (`flags`, `preparer.role_codes`) never separate rules, and text that reads as a decimal or ISO date compares as one, so rare codes such as "10" and "10.0" can be reported as a tie.
- **API-R-57 subject types.** `pob_template_version` and `account_mapping_version` return 422 on `subject_type` until RFD-10 and RFD-7 create their tables (XR-12). `registry_version` cases can be written while that version is DRAFT or TESTED.
