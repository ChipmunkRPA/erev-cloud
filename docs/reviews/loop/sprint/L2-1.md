### Spec questions

- **L2-1-Q-1.** 04 §16 defines no account mapping schema. `AccountMappingOut` returns the T-REF-14 and SC-V columns plus `pending_approval_request_id`, `rule_count` (§16.14), `created_at`, `created_by`, `updated_at` and `row_version`. `AccountMappingRuleOut` returns the T-REF-15 columns with `gl_account` as API-S-Ref (SCREENS §9.6 "<code> <name>"). `POST /account-mappings` answers 201 with `Location` and `ETag`; `POST …/rules` answers 201 without either, because API-R-20 has no single-rule read and rules have no `row_version` (DG-CMD-12). Request: confirm, or define API-S-AccountMapping, API-S-AccountMappingRule and API-S-AccountResolution.
- **L2-1-Q-2.** Effective-dated versions. T-REF-14 ("DB-04 rejects overlapping effective ranges among PUBLISHED versions"), T-REF-15 step 3 ("the PUBLISHED mapping version effective at … `recorded_at`") and the acceptance ("PUBLISHED version 1 effective 2026-01-01 and version 2 effective 2026-10-01") are read as several PUBLISHED versions with disjoint `[effective_from, effective_to)` ranges:
  - Publication ends the PUBLISHED version in force at the new `effective_from` there (its `effective_to`, audited `account_mapping_version.end`); it stays PUBLISHED. A PUBLISHED version starting at the same instant becomes SUPERSEDED.
  - Any other PUBLISHED version reaching past the new `effective_from` returns 409 `configuration-overlap` with `code = "EREV-CFG-001"` and `errors = [("effective_from", "DB-04")]`, checked before the DB-04 trigger backstop. A version effective before the earliest PUBLISHED one therefore always overlaps, because authors cannot set `effective_to`.
  - This departs from the RFD-5 `lifecycle.publish` supersede model (one PUBLISHED version per scope), so `mapping.py` implements `publish` and `approve` over the lifecycle primitives (`transition`, `mark_tested`, `submit`, `close`, `require_editable`).
  - Request: confirm; or rule the supersede model with SUPERSEDED versions counted within their range (the L1-4-Q-8 and D-80 SoD analogue), in which case the overlap fragment of `test_effective_dated_versions` cannot arise through the API.
- **L2-1-Q-3.** Publish lint ordering. `/publish` runs the REQ-POL-002 lint before the status check, so a DRAFT with ambiguous rules returns 422 (acceptance), while a clean SUBMITTED version returns 409 `invalid-transition` (CTL-031). `/test` runs the same lint and refuses TESTED with 422; T-REF-14 has no `lint_result` column, so findings are returned, not stored. Approval runs the lint again at publication. Request: confirm.
- **L2-1-Q-4.** Resolution tie-break. The publish lint refuses equal key columns only, so a product rule and a revenue-category rule of equal specificity and priority can both match a line carrying product and category. [J] The product rule wins, then the earliest rule (UUIDv7 id). Request: rule, or extend the lint.
- **L2-1-Q-5.** Resolve route semantics: an absent `entity`, `book`, `product` or `revenue_category` means the line carries no value, so only rules leaving that key null match (`book` does not default to the primary book); `entity` is a code or id (unknown: 422 on `entity`, T-REF-01); `known_at` defaults to now and must carry an offset; a clearing purpose on another role returns 422; reserved roles fail closed with `unmapped-account-role`. Request: confirm; in particular whether `book` defaults to the primary book.
- **L2-1-Q-6.** TC-JE-12 `errors[0]` members `contract`, `obligation_key` and `role` are not API-S-Problem error members (`field`, `sheet`, `row`, `rule_id`, `message`). `mapping.MappingProblemError` subclasses `ProblemError` with `contract`, `obligation_key`, `role`, `clearing_purpose` and `entity`, so `problems.py` and `ProblemErrorOut` are unchanged and OpenAPI does not list the extra members. The message is ERR-46 with the SCREENS role label, the purpose label in parentheses for `BILLING_CLEARING`, and the entity code or "any entity". An override naming an account that is not visible fails closed with the same problem. Request: confirm, and amend the API-S-Problem error members.

- **L2-1-Q-53.** Parameters. T-REF-32 `parameters` names no book and no pool file, but SCREENS §11.5 shows "SSP book (select)" and "Pool file (upload)", and J-02.3 creates the draft in the run's book. [J] `parameters` adds:

- **L2-1-Q-55.** Pool file format. BS3-D-15 names only `order_line_external_id`. [J]:
  - Columns, header names exact. Required: `order_line_external_id`, `order_date` (YYYY-MM-DD), `product_code`, `quantity` (above 0), `unit_price` (at least 0; ASCII digits, at most 18 decimals), `currency` (ISO 4217). Optional: `entity_code`, `customer_code`, `stratification`, `region`, `channel`, `segment`, `deal_size_band`, `term_band`. Other columns are ignored. A byte order mark is allowed, and an order line appears once.
  - A row is an observation when its product is among `product_ids`, its date lies within `[date_from, date_to]`, its currency equals `currency`, and every `dimensions` filter equals the row's value (`entity` reads `entity_code`). Unknown products are not findings.
  - Statistics use unit prices; quantity is only shown.
  - A malformed file fails the job with 422 `validation-failed` errors (`row`, `field`, rule `BR-SSP-04`, at most 100), and the run ends FAILED. The content must still match the file's SHA-256.

- **L2-1-Q-56.** Statistics. REQ-SSP-009 names the measures but not the methods. [J]:
  - Percentiles and the median interpolate linearly between the closest ranks, h = (n − 1) × p (Hyndman and Fan type 7, as PERCENTILE.INC). This reproduces the WLD-X-24 medians.
  - The mean is arithmetic. The band is median × (1 ± `band_ratio`). Inside counts the non-excluded observations in [low, high], inclusive; compliance = inside ÷ observations.
  - Every value is rounded half up at the `erev.exact` scale (18 decimals).
  - The histogram has 10 equal-width bins from the lowest to the highest non-excluded price. Each bin holds its `from` value, and the last bin also its `to` value; equal prices give one bin.
  - Results are grouped by product, stratification, dimension key (the run's `dimensions`) and currency.
  - Request: confirm the percentile method and the bins.
- **L2-1-Q-57.** Exclusions. SCREENS §11.5 says the exclude modal "recomputes (job)", while 04 API-R-27 lists only the run as asynchronous. [J] `POST …/exclusions {source_reference, reason}` recomputes in the same request:

  - The reason has at least 10 characters after trimming.
  - The observation is named by its order line id. It must exist, must not already be excluded, and may not be the last non-excluded observation of its product and key (each 422).

  - An exclusion cannot be withdrawn, because T-REF-34 is IM-A.
  - Request: confirm synchronous recomputation and the latest-row rule, and rule whether exclusions may be removed.
- **L2-1-Q-58.** Draft version. [J] `POST …/create-draft-version {version_label (R), effective_from_date, effective_to_date, methodology_label}`:

- **L2-1-Q-59.** Linked-run coverage (POLICIES §3.3; PRD J-02.5 rev 1.3; completes L2-1-Q-37):
