### Spec questions

- **L7-2-Q-1 (exception scoping for the close).** 04 API-S-Period names `exceptions_open` without a scope. [J] An item counts while `OPEN` or `IN_PROGRESS` with severity `BLOCKING` or `WARNING` (the severities a waiver clears; DIN-11), for the entity (`entity_id`, or a contract of the entity when the item names no entity) and the period (`period_id` null or the period). `INFO` items and items scoped to no entity (import-level items) do not count; a failed import's `CONTROL_TOTALS_MISMATCH` counts as an interface failure instead (Q-3). `unmapped_products` counts the `PRODUCT_UNMAPPED` items of the same scope, so such an item is in both counts; the SCREENS_B §1.1 "each item appears once" arithmetic belongs to the SF-05 blocker rows (CLO-23).
- **L7-2-Q-2 (pending approvals of an entity).** Most `SUBJECTS` entries name no entity on the request (L4-2-Q-5, L5-2-Q-4, L6-3-Q-9), so `approval_request.entity_id` cannot scope BLK-01. [J] A PENDING request counts when it names the entity, or names no entity and its subject is a contract, event submission, obligation, policy override, estimate version, judgement record, journal run, manual adjustment, checklist item or exception item of the entity. Tenant-wide subjects (configuration versions, roles, imports) do not count.
- **L7-2-Q-3 (CTL-002 `sync_run` half; R-RC-1).** T-INT-02 `sync_run` waits for DIN-12 (post-rc, L6-1-Q-11), so no sync run can be written or counted. The import half is built: `interface_failures` = FAILED imports whose `CONTROL_TOTALS_MISMATCH` item is still open, for every entity and period (imports name no entity; fail closed, XR-12). `test_ctl_002_failed_interface_run_fails_gate` asserts the import half; DIN-12 re-runs it with a `sync_run` of the entity in `CONTROL_TOTAL_MISMATCH`.
- **L7-2-Q-4 (gates while no journal run exists).** Header XR-12 and the item's fail-closed test require a journal run. [J] `JE_BALANCED` fails with count 1 and "Journal run not calculated"; `BATCHES_ACKNOWLEDGED` fails with the unacknowledged batches of non-cancelled runs plus 1 and the same detail. With a run, `JE_BALANCED` counts the unbalanced batch currencies and `BATCHES_ACKNOWLEDGED` the batches not acknowledged. The SCREENS_B §1.1 wireframe ("7 of 13 passed", `JE_BALANCED` and `JUDGEMENTS_REVIEWED` passed) differs from the BUILD_SPEC figures for the WLD-B tenant, which govern.
- **L7-2-Q-5 (when checklist items exist).** T-CLS-03 stores results and ids are UUIDv7 (NC-04), while queries never write (DG-CMD-13). [J] The routes of `GET /periods/{id}/cockpit` and `/checklist` check that the reader sees the period, then run `commands.refresh_checklist` as the SYSTEM principal in its own unit of work (the CLO-5 "cockpit refresh through a command" pattern), then read. The refresh creates missing items with `INSERT … ON CONFLICT DO NOTHING` and writes an automatic item only when its status, count or detail changes, with one audit event per affected item; `result.evaluated_at` is the time the stored result was established. A `future` period has no checklist (SCREENS_B SCR-ST-03 empty checklist), and a `closed` or `permanently_locked` period is not evaluated again (certification at lock, CLO-6). Sign and waive evaluate the gates before they act.
- **L7-2-Q-6 (due dates).** T-CLS-02 `due_offset_days` counts business days after period end. [J] Monday to Friday; no holiday calendar exists.
- **L7-2-Q-7 (checklist waiver requests; BS4-D-07).** [J] A checklist waiver request names no entity, as L4-2-Q-5 and L6-3-Q-9 ruled, because `approval_queries._entity_ref` still refuses a request with an entity (XR-12); the step permission `exception.waive` is then checked tenant-wide.
