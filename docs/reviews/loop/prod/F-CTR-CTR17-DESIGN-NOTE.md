## (b) Guided classification — the engine's rules, no new accounting

The classification is the engine's existing decision tree, read back as a proposal; the platform records the answers, stores the proposal and enforces the departure rule. Rules (ENGINE_SPEC §6.2, `docs/accounting/ENGINE_SPEC.md`):

- **S06-R-01 Proposal and choice** (`:1285`): the engine proposes per obligation (E-23) and returns it in `proposals` (CV-16); `CONTRACT_AMENDED.treatments` carries the approved chosen treatments; a departure from the proposal requires a reviewed judgement record of topic `MODIFICATION_TREATMENT_OVERRIDE` before approval (REQ-MOD-002; platform).
- **S06-R-04 25-12 test** (`:1288`): separate contract when every line is `ADD` of distinct goods (questionnaire `added_goods_distinct`, default from the resolved template distinctness), no existing obligation changes, and every line passes POL-101 `WITHIN_MOD_DATE_RANGE` (`resolve_ssp(at = d, ΔQ_m, ΔC_m)` range / point tolerance) or `priced_at_ssp = true` ("the preparer's approved attestation of an SSP adjusted for the circumstances of the contract").
- **S06-R-05 Classes S, D, N** (`:1289`): S = satisfied and no quantity change (`MOD_QTY_ON_SATISFIED_POB` ERROR otherwise); D = remaining goods distinct (`remaining_goods_distinct_from_transferred`, defaults stated); N otherwise. Route label: all D `PROSPECTIVE` (25-13(a)), all N `CUMULATIVE_CATCH_UP` (25-13(b)), otherwise `MIXED` (25-13(c)).
- **S06-R-03** (`:1287`): a chosen `SEPARATE_CONTRACT` is not applied by the engine — the platform books a new contract (own group, `origin_modification_id`) and appends nothing to the original stream; a `CONTRACT_AMENDED` carrying `SEPARATE_CONTRACT` is a programming error (CV-45).
- **S06-R-06 / S06-R-07** (`:1311–1312`): SSP basis D-18 (`D18_DEFAULT`, per-obligation override in `ssp_basis` with justification); lines with signed ΔQ / ΔC, `price_change_amount` and the questionnaire member `price_change_settlement`.
- **S06-R-19** (`:1329`): subscription kinds (E-25) have prescribed line shapes; `propose` raises `ValueError` otherwise (`s06/__init__.py:266–267`).
- **§6.5 S06-R-28 to S06-R-31** (`:1390–1393`): legacy templates under POL-100 `USER_SELECTED_TEMPLATE` — parity only; a native modification never sets `template_mode`.

Platform flow (SM-03): `POST /contracts/{id}/modifications` creates a DRAFT (contract `ACTIVE`; modification-date SSPs resolved, D-18); `PATCH` edits questionnaire / lines while DRAFT; `/classify` builds the `ModificationInput` from the row and runs the engine with NO applying event (§c's dry run carrying the row as a pending native T-CON-06 input — `bundles.build(…, pending_modifications = (row,))`, an empty pending-event tuple — so that stage 13 `_pending_proposals` proposes for the bundle modification no event of the stream applies, measured over the state after the fold; `propose` needs `ctx` / `st` / `identified`, which only a compute provides; amended in place 2026-09-21 per Codex production-20260921-1608 §1 / D-98 140-A2 — the earlier text had the candidate `CONTRACT_AMENDED` pending, which applied the modification during classification), stores `proposed_treatments`, `treatment_summary`, the D-18 `ssp_basis` defaults, and initialises `chosen_treatments` = proposed; a `chosen_treatments` departure without a reviewed `MODIFICATION_TREATMENT_OVERRIDE` judgement makes `/submit` return 422 `rule_id = "REQ-MOD-002"` (BUILD_SPEC test). The engine's `propose` docstring (`s06/__init__.py:261–267`) is the decision tree the wizard shows; no rule is added, reworded or defaulted differently by the platform. Accounting question raised: none — the questionnaire defaults and the S / D / N classes are the engine's (S06-R-04 / S06-R-05); should the wizard need a default the spec does not state, that is returned as a question, not chosen.

## (c) Impact preview — a DRY_RUN over the modified contract, same provenance, never posted

**Existing seams.** `domain/contracts/events.py:33–36`: `request_preview` (`POST /contracts/{id}/events/preview`) validates as `record_events` and defers `CONTRACT_COMPUTE` in mode `PREVIEW`, whose `run_preview` (`:1536`: "a dry run of the pending events; writes nothing") computes the group in `DRY_RUN` through `bundles.build(session, group_id, known_at, pending_events, DRY_RUN, pending_contract_id=…)` (`bundles.py:1200–1209`) and answers API-S-ImpactSummary (`impact_summary`, `:1401–1494`). `domain/contracts/estimates.py:854–875` uses the same seam with a version applied as if approved. `domain/policies/simulation.py:1–13`: the provider registry for configuration changes (`simulate`, REPORT_OUTPUT file, API-S-SimulationSummary; "CTR-16 registers the contract provider").

**CTR-17 preview.** `POST /modifications/{id}/preview` (202 job, API-R-31 "preview") = `run_preview`'s dry run with the candidate `CONTRACT_AMENDED` (built from the DRAFT / SUBMITTED row, S06-R-02 "ENG-12; REQ-MOD-013") as the pending event; the result is API-S-ImpactSummary plus the modification members BUILD_SPEC names (`transaction_price_before`, `transaction_price_after`, `catch_up_total`, remaining allocation per obligation — `test_preview_k02_upgrade_figures`), stored as an `IMPACT_PREVIEW` file whose SHA-256 goes to `impact_preview_file_id` / `impact_preview_sha256`; `/submit` without it returns 422 `rule_id = "REQ-PLT-015"`, with it the `MODIFICATION` request stores the file and hash (`test_submit_needs_preview_snapshot`; DG-KRN-APR-01). Provenance: the file carries the dry run's `engine_version`, `input_sha256`, the stream heads and group of the bundle, exactly as any computation's bundle does (CV-26) — but a DRY_RUN writes no `contract_computation` row, no version, no lines (`run_preview` "writes nothing"); posting happens only on approval through the ordinary computation, which writes its `contract_computation` row and versions (§f). A preview is therefore reproducible from its stored inputs but is never a posting. **Retained basis and freshness (amended in place 2026-09-21 per Codex production-20260921-1608 §1 / D-98 140-A2 and Codex 1713 CTR17-DOMAIN-R1).** The preview carries exactly ONE candidate applying boundary — the row's `CONTRACT_AMENDED` — beside the row as a pending native input (stage 13 skips the applied key, so the proposal is not duplicated). The stored `IMPACT_PREVIEW` document retains the candidate's canonical inputs or enough immutable references to reconstruct them: the engine version, the bundle `input_sha256`, the target contract id and head, the SHA-256 of the row content the candidate was built from (`content_sha256` of §f's subject content) and the consumed group basis — every member contract's id and stream head plus the group id (the §f subject content's members). `/submit` re-derives that basis under the protecting locks and compares it member by member: a stale preview (any member head moved, the row edited, the file's hash changed) is refused with 422 `rule_id = "REQ-PLT-015"` `PREVIEW_STALE` — never relabelled with the current heads. Approval re-verifies the same content hash (`assert_fresh_basis`, §f) before any effect. An authored edit resets the preview members to NULL (§b).

**Seam with CTR-16 and the proposed order.** CTR-16 (`docs/BUILD_SPEC.md:6738–6761`) registers the contract provider of `policies/simulation.py`: a dry-run `compute` over the affected groups of a read-only snapshot, the report attached to the configuration change (BS3-D-05 / BS3-D-17), plus `reruns.py` `apply_to_existing`. CTR-17 needs only the single-group dry run that `events.run_preview` and `estimates` already use; it does not need the multi-group provider. Both should call one helper — "dry run of one group with pending events, answered as ImpactSummary" — lifted from `run_preview` (no behaviour change) so that CTR-16's provider iterates it. Proposal: **CTR-17 before CTR-16** — technically independent of CTR-16; unblocks F-CLO's K03 / WLD-X-13 row (readiness `:312`: the J-06 modification `CR-CASTELLAN-2026-09` needs the CTR-17 path) which names no CTR-16 dependency; CTR-16 then registers its provider over the shared helper. This re-sequences BUILD_SPEC's "Prerequisites: CTR-16" line for CTR-17 — a docs move for the supervisor's ruling (Q-1). If the BUILD_SPEC order is kept, CTR-17 waits for CTR-15 → CTR-16 and nothing in this note changes.

## (d) Regrouping — P5's kernel order, cited, not re-implemented

`POST /contracts/{id}/regroup {obligation_keys, comment}` (API-R-28 `:5316`; REQ-CON-012 `docs/03-REQUIREMENTS.md:281`; BUILD_SPEC `test_regroup_before_posting_reruns_both`, `test_regroup_after_posting_creates_two_modifications`). Two cases, decided by the platform from persisted postings (the engine reads none, CV-14):

- **Before any line of either contract has posted:** append the paired `REGROUPED` events (`direction` OUT on the source, IN on `counterpart_contract_id`, shared `regroup_id`; `RegroupedV1` `payloads.py:677`; 04 `:5922`) and recompute both contracts from inception — the engine treats the moved obligations as booked in the target from its inception (S06-R-27 `ENGINE_SPEC.md:1337`; `regroup.py:6–9`); `stream.py:26–31` inserts the obligations the IN event names.
- **After posting:** create two T-CON-06 modifications (REMOVE lines on the OUT contract with ΔC = −moved remaining consideration; ADD lines on the IN contract with ΔC = +moved remaining consideration; S06-R-27) and return 201 `{modification_ids}`; each then goes through §b / §c / §f as ONE spanning `MODIFICATION` request (D-98 140 Q-4). On approval the pair appends exactly ONE applying boundary per side: the `REGROUPED` event (`direction` OUT on the source, IN on the target; shared `regroup_id`; each carrying its own row's `modification_id`; 04 `:5922` R) whose obligation lines are the referenced native T-CON-06 rows — the REMOVE / ADD lines the engine reads from the row through the bundle's native inputs; no `CONTRACT_AMENDED` is appended on either side. The pair's identity is the shared `regroup_id` (`ix_modification__regroup`; both rows in the one request's content); both sides apply in one unit of work under `lock_groups_then_contracts` — OUT before IN, the IN side's created obligations copied from the source — or neither (an `EngineError` rolls the decision back, so no side is APPLIED alone). Amended in place 2026-09-21 per Codex production-20260921-1608 §1 / D-98 140-A2 — the earlier text described a `CONTRACT_AMENDED` plus the `REGROUPED` pair per side, two applying boundaries.

Locking: the two contracts may sit in two combination groups, so the command takes P5's kernel order — `erev_api.db.locking.lock_groups_then_contracts` (`locking.py:72–108`: every group row FOR UPDATE in globally ascending id order, then the contract rows ascending, membership re-read under the lock and 412 `precondition-failed` REGROUPED on inequality; D-98 candidates 101a / 101c) — the same helper `combination._lock_groups_then_contracts` wraps (`combination.py:406–429`) and `void.py` / `activation.py` already use; `regroup.py` calls it and adds no lock logic of its own. The "posted?" test reads T-SL-04 `subledger_line` for either contract at the command's `known_at`.

## (f) Approval — the MODIFICATION SubjectSpec and the maker-checker relation to CTR-6

`SubjectSpec` fields (`subjects.py:183–209`): `subject_type=MODIFICATION`, `table="modification"`, `required_permission="modification.approve"` (PRD `:279`), `revenue_affecting=True` (impact preview required, REQ-PLT-015 — BUILD_SPEC `:6765` "`revenue_affecting = true`"), `min_approvers=1`, `entity_id` = `contracting_entity_id`, `amount_functional` = the preview's absolute transaction-price change in the entity's functional currency, `flags` = the PRD second-step conditions evaluated from the stored preview (`\|catch_up_total\|` ≥ 50,000.00; `\|ΔTP\|` ≥ 250,000.00 — representation question Q-5), `link_path` `/modifications/{id}`.

**Subject content (what the approver sees; `content_sha256`, DG-KRN-APR-01).** The T-CON-06 fields the preparer authored (`effective_date`, `kind`, `reference`, `lines`, `questionnaire`, `price_change_amount`, `price_change_settlement`, `noncash_consideration`, `consideration_payable`, `scope_605_35`, `proposed_treatments`, `chosen_treatments`, `treatment_summary`, `ssp_basis`, `rationale`, `judgement_record_id` with the judgement's `content_sha256`), the `impact_preview_sha256`, and — P5's pattern — the contract's `{combination_group_id, head_stream_version}` plus every member's group id and stream head (`judgement_record_subject_content` `subjects.py:1092–1114`; `combination_group_content` members; `_member_states`). Any append or regroup between submission and decision changes the hash → `decide` voids the request with `STALE_SUBJECT` and answers 409 `stale-approval` (DG-KRN-APR-02; CTL-007 test `test_ctl_007_stale_or_self_approved_modification_not_applied`); editing a SUBMITTED row voids the request the same way (`void_if_stale`, DG-KRN-APR-05; SM-03 SUBMITTED → DRAFT).

**Callbacks.** `on_approved(uow, modification_id, approval_request_id)` follows `void.py._approved` exactly: `lock_group_then_contract` (D-98 101c) → `approvals.engine.assert_fresh_basis` (101d) → status APPROVED → append `CONTRACT_AMENDED` (payload copied from the row: `treatments` = `chosen_treatments`, `lines`, `ssp_basis`, optional members) as the SYSTEM principal with `approval_request_id`, or for `SEPARATE_CONTRACT` book the new contract in its own group (`origin_modification_id`) and append nothing (S06-R-03), or for a regroup-after-posting pair append the ONE `REGROUPED` event per side (§d, amended 2026-09-21) → recompute → APPLIED with `applied_event_id`, or APPROVED "Quarantined" when the computation fails (SM-03; E-88). `on_rejected` → REJECTED; `on_voided` → DRAFT (withdraw / stale). The approved basis is captured after every system-side mutation in the same unit of work (DG-KRN-APR-05 rev 1.40).

**Relation to CTR-6 (manual event maker-checker, CTL-009).** CTR-6's `MANUAL_EVENT` subject (`subjects.py:2689–2702`, table `event_submission`, T-CON-24) covers events a preparer types in; approval appends them as SYSTEM with `is_manual = true`. A modification is not a manual event: its maker-checker is the `MODIFICATION` request itself, and its `CONTRACT_AMENDED` is appended by the approved subject's own callback (as `CONTRACT_VOID` appends `CONTRACT_VOIDED`) — one approval, not two; self-approval is refused by the approvals engine (403 `self-approval`, the CTL-007 / CTL-009 pattern). A later `EVENT_VOIDED` of an applied amendment goes through CTR-6's path (SM-03 last row).
