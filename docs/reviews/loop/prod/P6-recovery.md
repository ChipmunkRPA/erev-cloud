## 4. Implementation

### 4.1 `backend/erev_api/controls/recovery.py` (`06f1f41`)

- `verify_all_tenants(keyring, files, clock, request_id, database, engine_version, tenant_codes, check_files)` → the `erev-recovery-verify/1` document: `security_chain` (result, head seq/hmac, key served), `tenants[]` (`audit_chain` from the new public `audit.verify.verify_tenant_chain_anchored`, `head`, `digest` {seq, hmac, verified_at, file id, `event_matches`, `file.matches_row`}, `gap_events`, `ledger_chains[]` via `domain.journals.subledger.verify_ledger_chain` per `ledger_chain_head` book, `audit_hmac_keys[]` with `available`, `kek_ids`, `files` counts + entries with status), `key_versions` (security, audit per tenant, KEK ids from sidecars, webhook and MFA envelopes), `latest_evidence_at`, `result`, `failures[]`, `counts`.
- `check_file(row, files, keyring)` → status `ok | shredded | missing_object | missing_sidecar | shredded_sidecar_present | undecryptable | sha256_mismatch | size_mismatch` and the sidecar's KEK id.
- `anchor_requests(expected)`, `resolve_anchors(anchors, request_id)`, `compare_expected(expected, actual, anchors)` → the backup-time document anchored into a restored database: chains may be longer, never shorter; the row at each recorded head carries the recorded hash; every file recorded `ok` verifies with the same SHA-256; every recorded key is served.
- `record_restore_applied(...)` → `platform.restore_applied` per ACTIVE tenant as the SYSTEM principal through `unit_of_work` + `record_facts`, detail `{restore_instant, backup_id, previous_head, head_before_event, ids}`; returns previous and new heads. `previous_heads_of(document)`.
- `audit/verify.py`: additive `verify_tenant_chain_anchored`; `record_tenant_verification` unchanged in behaviour.

### 4.2 CLI (`cli.py`, `06f1f41`)

`_select_database(db)`: `dev|test|e2e` switch `EREV_ENV`; `erev_rv_*` selects the dev pair and exits 2 unless both dev URLs name that database (message names the rule, not the URL). `doctor --db` uses it. `verify --all-tenants|--tenant CODE… [--db] [--json] [--output PATH] [--expect PATH] [--files/--no-files]`: one `OK|FAIL <check>: <summary>` line per check, `OK verify` or `FAIL verify: <n> findings` (exit 1; exit 2 on usage). `restore-applied --instant RFC3339 --backup ID [--digests PATH] [--db]`: one JSON line per workspace, `OK restore-applied: <n> workspaces`.

### 4.3 Scripts and Makefile (`6dd5dcb`)

`scripts/backup.sh` steps (1)–(6) as in DG-MK-backup rev 1.3 (§7); `scripts/restore_verify.sh` steps (1)–(6) as in DG-MK-restore-verify. Both `set -euo pipefail`, write their DG-MK-00g report on success and failure, print only file names and stage messages, build `PG*` variables inside Python from the URL, and never take a URL as a command-line argument. Makefile: `backup` and `restore-verify` (`BACKUP`, `RESET`) with the D-48a banner first; `.PHONY`; `BUILT_TARGETS` and `PHASE_TARGETS["DEP"]` extended in `test_makefile_targets.py` (BS1-D-11). `.env.example` gains a commented `EREV_BACKUP_URL` line.

### 4.3a `scripts/check_env.py --db` (`92f44e1`)

`check_recovery_urls(env)` → `(notes, errors)`: `recovery URL absent: <name>` for a missing `EREV_BACKUP_URL` or `EREV_RESTORE_ADMIN_URL` (a note, not a failure); errors for a non-`postgresql://` URL, a database outside the allow-list or a redirecting query parameter, a backup URL naming another database than `EREV_DB_OWNER_URL`, or an admin URL naming anything but an `erev_rv_*` database. Errors exit 1 with the allow-list errors, before any connection; success prints `recovery URLs OK: <names>`. Measured on this worktree: absent → two notes then `databases OK: erev, erev_rv_p6_test, erev_rv_p6_e2e`; with the drill URLs exported → `recovery URLs OK: EREV_BACKUP_URL, EREV_RESTORE_ADMIN_URL`.

## 7g. Cloud SQL and `BYPASSRLS`: the hosted recovery provider (ruling D-95)

**Premise as corrected by Codex's note (`PRODUCTION-OPR15-CLOUDSQL-PRIVILEGE-NOTE-20260919.md`) and adopted here:** PostgreSQL 17 `CREATE ROLE` requires `CREATEROLE` or superuser, and specifying `BYPASSRLS` additionally requires the creator to be a superuser **or to already hold `BYPASSRLS`**; `ALTER ROLE` lets a non-superuser change `BYPASSRLS` only when it holds the attribute itself; attributes are not inherited through membership, so `CREATEROLE` alone cannot bootstrap it. Cloud SQL gives customers no `SUPERUSER`; its documented `postgres` attributes are `CREATEROLE`, `CREATEDB` and `LOGIN`, `cloudsqlsuperuser` is not PostgreSQL `SUPERUSER`, and Google documents no customer `BYPASSRLS` bootstrap procedure. The native backup role on Cloud SQL is therefore **unestablished, not proven impossible**, and the design does not depend on it (this record's earlier "superuser-only"/"impossible" wording is withdrawn). `FORCE ROW LEVEL SECURITY` binds the owner, `pg_read_all_data` grants reads but not `BYPASSRLS`, `row_security = off` makes an affected dump fail, and `--enable-row-security` yields only the rows the identity may see. The lane's live measurement stands: `pg_dump` as `erev_owner` is refused under DB-14.

**Applied on this branch (D-95 adjustments 1, 2, 3, 5):** the explicit recovery provider `EREV_RECOVERY_PROVIDER ∈ {NATIVE, MANAGED}` (`recovery_preflight.resolve_recovery_provider`: default `local` → NATIVE, `gcp` → MANAGED; a contradicting explicit value or an unknown value is a configuration error); `check_env --db` requires both recovery URLs under production+NATIVE, refuses a set value under MANAGED and notes the managed-drill inputs as unknown (UI-P6-2); `make backup` and `make restore-verify` refuse under MANAGED before anything runs; the MANAGED provider is a **mock with the record contract** (`erev_api.controls.recovery_managed`: `ManagedBackup`, `ManagedRestore`, `ExternalState`, `Assurances`, `ManagedRestoreRecord.document()`, `validate_managed_record`, `MockManagedProvider`, `build_managed_record`) whose acceptance cases are the ones the note lists: provider selection; a pending, failed or wrong-instance backup refused; destination isolation (fresh instance, other instance and project); complete bindings (project, instance, id or PITR instant, operation status, start and end, engine, schema, release); restore point = PITR instant or backup completion and never the record instant; drifted file generations, unserved key versions or absent digest anchors refused; a failed or unanchored verification refused; no bypass, partial dump, relaxed policy or impersonation; `managed_bytes_sha256` must stay null (never an invented hash of managed bytes).
