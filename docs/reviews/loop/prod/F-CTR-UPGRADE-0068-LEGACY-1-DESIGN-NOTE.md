## 3. Candidate A — a STORED GENERATED native-only reference column (Codex 0315 §5–§6)

Design. A new revision (number assigned by the supervisor) adds to `contract_event` a stored generated column — working name `native_modification_id uuid GENERATED ALWAYS AS (erev.native_modification_reference(event_type, payload, modification_id)) STORED` — where the IMMUTABLE SQL function returns NULL when the event is an exactly-recognised legacy-template amendment (F7: `event_type = 'CONTRACT_AMENDED'` and `payload->'treatments'` is a non-empty object whose values all lie in the legacy set) and `modification_id` otherwise; drops `fk_contract_event__modification` from `modification_id` and recreates the tenant-composite FK (MATCH SIMPLE, ON DELETE RESTRICT ON UPDATE RESTRICT) on `(tenant_id, native_modification_id)`. The original columns are never rewritten (R1, R3); native rows keep FK integrity through the generated value (R4); the bundle's payload-based refusal stays (R5); the forward NULL (F13) stays.

Recognition. The expression must reference the row's own columns only and use immutable functions: a SQL-language function declared IMMUTABLE over `jsonb_each_text` satisfies PostgreSQL; the legacy set is a literal in the function (E-23 legacy labels: `LEGACY_PROSPECTIVE`, `LEGACY_RETROSPECTIVE`, `LEGACY_POB_PRICE_CHANGE` — the labels must be mirrored from `TEMPLATE_MODES`, with a drift pin like DG-SM-04). Cross-row provenance (does a row of that id exist?) cannot live in the expression — that is exactly why the Q-3 refusal stays in the bundle (Codex peer-check).

DDL sketch (owner, one transaction — `transaction_per_migration = True`):
1. `CREATE FUNCTION erev.native_modification_reference(event_type text, payload jsonb, modification_id uuid) RETURNS uuid LANGUAGE sql IMMUTABLE …` (+ the §14.2 REVOKE / grants as for every function).
2. `ALTER TABLE erev.contract_event ADD COLUMN native_modification_id uuid GENERATED ALWAYS AS (…) STORED` — ACCESS EXCLUSIVE lock and a FULL TABLE REWRITE of `contract_event` (every existing row is computed); duration proportional to the event table; maintenance window on production; no row's original columns change.
3. `ALTER TABLE erev.contract_event DROP CONSTRAINT fk_contract_event__modification`.
4. `ALTER TABLE erev.contract_event ADD CONSTRAINT fk_contract_event__native_modification FOREIGN KEY (tenant_id, native_modification_id) REFERENCES erev.modification (tenant_id, id) ON DELETE RESTRICT ON UPDATE RESTRICT` — validated (F9 wants one shape on every path).
5. Downgrade: reverse (drop the new FK, drop the column, drop the function, re-add the old FK) — which on a DB holding legacy synthetic ids FAILS at the re-add (the same F1 validation); DG-MIG-08 says downgrades run only in the round-trip test, where no such rows exist.
Companion changes: ORM `Column("native_modification_id", Uuid(), Computed(…, persisted=True), nullable=True)` (F8; DG-ARC-15 renders it); the insert path excludes the generated column (SQLAlchemy omits `Computed` columns from INSERT — a witness); `ALIASES["native_modification_id"] = "modification"` (F5) and — for the OLD column — a decision: `modification_id` stays a reference for native rows but is a TOKEN for legacy rows, so the references pass needs a PER-ROW rule (a legacy-recognised row's outer id is neither resolved nor reported broken; the generated column carries the reference) — a new mechanism beside `TOKEN_COLUMNS` (F5); privacy CLASSIFICATION gains the column (F11); API-S-Event keeps exposing `modification_id` (the outer column: the row id for native events, NULL for new legacy events, the historic synthetic id for pre-0068 legacy events — three meanings, which 04 must state) — or the API exposes the generated column instead (a schema change; not recommended).

Witness plan (tests/pg, lane DB, slot 2): (W1) generated value = `modification_id` for a native row, NULL for a legacy-template row (both inserted through `contract_event_values`); (W2) the new FK refuses an unlinked native id (23503 naming `fk_contract_event__native_modification`) and admits a legacy row whose OUTER column carries a synthetic id with no row — the exact pre-0068 shape; (W3) DG-MIG-05 round trip equal; (W4) DG-ARC-15 agreement with `Computed`; (W5) a snapshot export → restore of a legacy row with a synthetic outer id into a head-schema sandbox succeeds and the references pass reports no broken finding (the per-row token rule); (W6) the drift pin: the SQL function's legacy label set equals `TEMPLATE_MODES`' legacy keys; (W7) FK-on-generated-column admissibility on PostgreSQL 17 (F12) — measured, not assumed.

## 4. Candidate B — no schema change; the legacy token handled at the snapshot boundary only

Keep the landed FK on `modification_id`. Handle history where it is met: a pre-0068 legacy row exists only (i) in a below-0068 database or (ii) inside an old sealed snapshot. For (ii), the restore already transforms references while loading (deferred references are inserted NULL; references to regenerated targets are nulled on export — F5/F6 precedent): add the PER-ROW rule "a legacy-recognised `CONTRACT_AMENDED` row is loaded with the outer `modification_id` NULL; the payload (and its hash) is unchanged", so the copy converges with the forward-fix shape (F13) and the sealed bytes are untouched (R3); the references pass treats the row as a token (R6). No DDL, no rewrite, no new column; R1/R2/R4/R5 hold trivially. It does NOT help (i): a below-0068 database still cannot pass 0068 as landed — see §5. B is therefore complete only if the population (i) is EMPTY (F14).

## 5. Convergence — the crux (R7)

| Database state | Candidate A | Candidate B |
|---|---|---|
| Fresh (`upgrade head`) | 0068 as landed (FK on the old column, no rows) → the new revision moves the FK to the generated column; round trip equal (F9) | unchanged |
| Already upgraded through 0068 (no legacy rows by construction — 0068 validated them absent) | the new revision converges (rewrite + FK move); identical catalogue to fresh | unchanged |
| BELOW 0068 holding legacy rows with synthetic ids | **cannot reach the new revision: 0068's step 222 fails at validation (F1)**. Only an edit of 0068 (or a new revision inserted BEFORE it, which also edits 0068's `down_revision`) lets such a database converge — a landed-revision edit that DG-MIG does not admit and the supervisor's regeneration exception does not cover; `NOT VALID` at 0068 diverges the catalogue (F9) and leaves the token rows violating on any later validation | same: B does not touch 0068 |

So the honest answer to "must 0068 itself change?": for a fresh or already-upgraded database, NO under A or B; for a below-0068 database holding legacy rows, YES under any design — and that edit is exactly what the governed text forbids. The population in question is F14's open question. Recommendation for the ruling: (1) settle F14 first (Ray: the dev DB's alembic revision and whether legacy Contract Modification imports exist there; any other below-0068 database) — read-only, Ray-side; (2) if EMPTY: no 0068 change; adopt B's per-row token rule at the snapshot boundary (it is needed under both candidates for old sealed snapshots) and DEFER A — a schema change with a full rewrite of the event table buys nothing that B does not, while adding a third meaning to the API column; (3) if NOT EMPTY: escalate as a ruled DG-MIG exception (a one-time, documented, convergent edit of 0068 that creates the FK on the generated column from the start, with A's new revision converging already-upgraded databases; the round-trip test proves fresh == upgraded) — Ray's ruling, not the lane's.
