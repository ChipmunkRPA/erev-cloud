# VC113-CAND109B-PROPOSAL — the JET-04b contract-liability leg resolves the owning obligation's account override (REVIEW DRAFT, not applied)

Lane F-CTR, on the supervisor's instruction (Codex packet 1510 item 2): a concrete isolated proposal for how the JET-04b `CONTRACT_LIABILITY` leg of a refund-liability component keyed `<group>@<entity>/CONCESSION/<event>/<obligation>` resolves POB #2's override **21002**, preserving VC-CHK-113's original 21002 expectation and the separate October question. **Not applied, not merged, not approved; a separate decision from candidate 109.** Companion patch: `VC113-CAND109B-CODE-DRAFT.patch` (284 lines, 3 files: `s14_posting/intents.py`, a new test module and one case appended to `test_s14_entries.py`; base c0de02a1).

## 1. The gap

Stage 14 resolves a line's account through `accounts.resolve(ctx, obligation, key)` (T-REF-15: step 1 the obligation's `account_overrides`, step 3 the mapping rules). `intents.py` finds the obligation by `obligations.get(subject_key)`; a refund-liability component's subject is the component key, so the lookup is None and step 1 never runs — the JET-04b `CONTRACT_LIABILITY` leg of a CONCESSION component takes the mapping default (2100) although the component's source names the obligation (POB #2) whose override is 21002. Stage 14 already knows the ownership rule elsewhere: S14-R-26 rev 1.18 / D-98 35a (`onboarding.COMPONENT_OBLIGATION_OWNED` = RETURN, CONCESSION, UNCLAIMED_PROPERTY resolve to the obligation their source names; `assign._component_contract` parses the same key form). The gap was invisible while the release never posted (109's diagnostic) and appears the moment 109 restores it.

## 2. Source (the patch)

`intents.py`: `_owner_obligation(st, subject_key)` parses `<group>@<entity>/<KIND>/<source>` and returns the owning obligation by EXACT CV-21 encoded identity: for RETURN / UNCLAIMED_PROPERTY the source IS an obligation subject key of the state (dictionary lookup); for CONCESSION the source is `<event key>/<obligation subject key>` where the event key must be an event of the state and the remainder an obligation subject key of the state — no suffix or substring guess, no lookup through openings (a contract without a baseline resolves the same way), and None for TERMINATION / VARIABLE_CONSIDERATION and for every non-component subject. In the line loop, when the subject is not an obligation, the owner is consulted **only for a role the owner overrides**: `resolve(ctx, owner, key)` (step 1 through the owner); every other path — the mapping rules with the component's contract-scope dimensions, the line's own dimensions (no `obligation_key` dimension is added), the subject (still the component key), `missing` — is unchanged. A first, broader variant that passed the owner into `resolve` for every role changed a RETURN component's line dimensions (`obligation_key` appeared) and failed `test_l9_run_q4_multi_member_refund_component_lines_carry_contract_key`; it was narrowed to the override step, and that test passes again untouched. **Dimension policy, declared and QUALIFIED (Codex 1541 (2); PRODUCTION-VC113-CAND109B-SOURCE-REVIEW-66c077ff.md, SHA256 a9f6c9b9d26d68f87f997860b021f2dc00eafe1d60a6a4b886bd29463943dc21; manifest 7eb0da467e0897c6eddb005a22df2d9fbc60c8b492e21ee4c365573b771cc1ff; 11 artifacts — no new concrete financial defect in the bounded canonical path):** `intents.py` passes its `obligation` variable to `_dimensions`; this proposal leaves that variable None for a component subject (the owner is a separate local used only for the override step), so no `obligation_key` dimension is added and the contract-scope dimensions (`contract`, `contract_key`, `product`) stay. But `_dimensions` STARTS from `resolution.default_dimensions`, and `accounts.resolve` returns `{}` for an owner override while it returns the selected rule's `default_dimensions` for a mapping resolution — so a dimension the OLD rule alone supplied (for example a department default) is ABSENT on the contract-liability line when the owner override wins. That is the existing T-REF-15 precedence (step 1 before step 3), not a new arithmetic defect; the proposal does not copy unselected-rule defaults to support an "unchanged dimensions" claim. The blanket statement "line dimensions unchanged" is therefore withdrawn in favour of: subject, netting, amounts, contract-scope dimensions and the absence of `obligation_key` unchanged; rule-default dimensions follow the resolution that wins. **Posting identity, unchanged:** the role key, the component key, the JET-04b per-component netting and the amounts are as before.

## 3. Spec sentence (draft, for ENGINE_SPEC_B §14.2.4 S14-R-09 / 04 T-REF-15 note)

"Step 1 (the obligation's account override) also applies to a line whose subject is a refund-liability component an obligation owns (`RETURN`, `CONCESSION`, `UNCLAIMED_PROPERTY`), the owner being the obligation the component key names by exact CV-21 identity (RETURN / UNCLAIMED_PROPERTY: the source is the obligation subject key; CONCESSION: `<event key>/<obligation subject key>` with the event an event of the computation); this ownership reading is stage 14's own and needs no opening baseline (S14-R-26 / D-98 35a define ownership for OPENING / CUTOVER; the same identities, independently resolved). The owner's override for the line's role is taken; without one the line resolves exactly as a component subject does today — step 3 mapping rules under the component's contract scope (the product / revenue category every obligation of its one member contract shares, else none; JET rule R3, L5-5-Q-8), never the owner's own product or category. Contract-owned kinds (`TERMINATION`, `VARIABLE_CONSIDERATION`) infer no obligation. The role key's subject stays the component key and JET-04b nets per component as before. Dimensions: the line keeps the contract-scope dimensions of a component subject (`contract`, `contract_key`, `product`) and carries no `obligation_key`; its rule-default dimensions follow the resolution that wins — the owner override contributes none, so a default the mapping rule alone supplied is absent when the override is taken (T-REF-15 step 1 before step 3, unchanged precedence)."
