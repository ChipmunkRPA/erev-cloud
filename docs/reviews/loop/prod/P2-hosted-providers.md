Logging: every new log line carries names, generations, statuses and counts only (`bucket`, `storage_key`, `generation`, `object`, `status`, `secret_id`, `version`, `attempt`); registered per logger with `register_logger_fields`; `secret` itself is a DG-LOG-07 forbidden key and is never used. `repr(Settings)`, `repr(GcpSecretManagerStore)` and every error message are value-free; the tests dump captured events and assert the master key, the tenant key material, the DEK, the plaintext and the app-URL credential never appear.

### 4.2 Secret references (`adapters/secrets/store.py`)

`GcpSecretManagerStore.get(ref)` parses `<name>@<version>` (`SECRET_REF`), refuses anything else with `SecretRefError` (whose message never echoes the reference, since a malformed reference could be a pasted value), and accesses `projects/<project>/secrets/<prefix><name>/versions/<n>`. `get_version(name, n)` requires `n ≥ 1`. `NotFound` → `KeyError(name)`; denied and outage → `GcpError` by kind. `GcpKeyProvider.secret(ref)` applies the refusal list (`app-kek`, `security-hmac`, `audit-hmac-*`, `db-owner-url`, `db-app-url`) to the name part, so a version suffix cannot bypass it. `latest` is read nowhere; the fake raises if it ever is.

### 4.3 `GcsFileStore` (`adapters/storage/gcs.py`) — contract rows to client calls

| Contract row | Implementation | Client calls (google-cloud-storage names) |
|---|---|---|

`storage_backend` of new rows is `"gcs"`. Storage keys pass the same segment rule as the local store (`check_storage_key`). Files are read whole into memory on open (purpose limits bound them; noted as a residual).

### 4.4 Lifecycle (`files/lifecycle.py`, `files/store.py`)

- Marker: `<storage_key>.dek.shredded`, create-if-absent, content `b"erev shred marker\n"`. `_file_key` (the shared writer path of `put_file`) refuses an upload that meets the marker with 409 `invalid-transition` `FILE_SHREDDED`; `open_file` maps a missing sidecar plus marker to 404 `not-found` `FILE_SHREDDED` (a database restored to before the shred).
- `rewrap_sidecar(files, keyring, storage_key, tenant_id=)`: marker check → live generation `g` (0 → `FileNotFoundError`, nothing to rewrap and nothing created) → read `g`, unwrap → `KeyRing.wrap_file_key(dek)` (same DEK, current KEK) → `replace(g)`; on `GenerationConflict`: live 0 → `FileShredded`; a winner with the same DEK → `changed=False`; a winner with a different DEK → `GenerationConflict` (inconsistency, never accepted). After a successful CAS the marker is checked again: if a shred landed in between, the rewrap deletes the generation it just created and raises `FileShredded`.
- `shred_sidecar(files, storage_key)`: marker first (so any concurrent writer refuses from now on), then up to five enumerate-and-delete passes over every generation that is not already soft-deleted, then a live-generation check (must be 0), then the report: `deleted_generations`, `retained` (soft-deleted generations with `hard_delete_at`), `irreversible_after` (the latest hard-delete time, `None` locally), `marker_created`. Idempotent. The payload and the `file_object` row are never touched (D-43).
- Serialisation: `lock_storage_key(session_or_connection, storage_key)` = `pg_advisory_xact_lock(<63-bit sha256 prefix of the key>)` for the shred/rewrap command's transaction (SOP-5, lane P8, wires the command; the pg test proves the lock blocks a second writer of the same key only).
- Local backend: one generation while the file exists (`LOCAL_GENERATION = 1`), `replace` = spool + `os.replace`, `delete_generation` = unlink, `versions` = the one live version; `LocalFileStore.put/open/exists` semantics and tests unchanged.

### 4.5 SAR-31 digests (`audit/digests.py`, `adapters/storage/digests.py`, `audit/verify.py`)

Name `<tenant id>/<YYYY>/<MM>/<DD>/<sha256 of the digest bytes>.json`. `GcsDigestExporter.export` (worker, `objectCreator`): create-only upload; 412 → `pending_verification` with the name and hash recorded (the creator cannot read the winner; nothing overwrites or deletes); transient → same-precondition retry; denied/other → `GcpError`, which fails the job attempt so SCH-01 retries and re-verifies (the digest name is deterministic, so a lost response resolves to `pending_verification`). `GcsDigestVerifier.verify(name, expected_sha256)` (a separate identity with `objectViewer`; P3 gives it to the api service account) reads the live object at its exact generation and reports `verified | mismatch | missing` with generation and size. Wiring: `JobRuntime.digests` (built by `worker.build_runtime` under `gcs`, `None` locally) → `audit_chain_verify` → `record_tenant_verification(..., digests=)`, which exports after `put_file` and before the T-PLT-23 row, logging `audit.digest_export_recorded {tenant_id, object, status, generation}`.

### 4.6 Tenant key bootstrap (`adapters/secrets/provision.py`, `auth/keyring.py`, `domain/platform/provisioning.py`)

Workflow of `GcpTenantKeyProvisioner.provision_audit_key(tenant_id)` under the provisioning identity: (1) `create_secret` `<prefix>audit-hmac-<tenant id>` with `user_managed` replication in the KEK's location (derived from `EREV_GCP_KMS_KEK`; `global` refused, PRV-10) — `already_exists` is fine, the secret is then `get_secret`-verified; (2) `list_secret_versions`; (3) no version at all → `add_secret_version` with 32 random bytes as 64 lowercase hex; if a concurrent provisioner made ours version 2, version 1 is used and the surplus is left in place with a warning (the role cannot destroy, and nothing erases material blindly); (4) version 1 exists but is not `ENABLED` (DISABLED, DESTROYED) → `malformed`, nothing added; (5) `access_secret_version` version 1, verify 64 hex → material. `HostedTenantKeyProvisioner` then reads the key back through the key ring (accessor path, version pinned by the key id) and requires equality (`ProvisioningReadbackError`). `provision_tenant` opens its `platform_session`, inserts the tenant row first under the deterministic key id `audit-hmac:<tenant id>:1` — so `ux_tenant__code` refuses a duplicate before the provisioner ever runs and a repeated request creates nothing anywhere (DG-KRN-TEN-02; a directory read is not available in the provisioning scope, see §6.1) — then runs the provisioner inside the same transaction and requires the returned id to equal the stored one: a provisioning failure rolls the row back, so a tenant commits only when its key can be read; no orphan secret is created for a duplicate code. Local `DerivedTenantKeyProvisioner` proves the HKDF derivation and returns `audit-hmac:<tenant id>:1` (DG-KRN-KEY-06 unchanged locally). Error surface: `TenantKeyProvisioningError(kind, secret, detail)`; the CLI prints it and exits 1; the operator route returns the generic 500 (no catalogue slug exists for an upstream dependency failure — question §9).

### 4.10 Codex review of 76cbee4 — writer admission (separate work item from F01–F04)
