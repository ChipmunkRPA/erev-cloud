### ENG-C1b integration barrier (named)

The import channel is complete on main's schema for `value_basis`; the `quantity_unit` half is admission-complete but
**cannot persist or round-trip until ENG-C1b merges**: main's E-49 holds `AMOUNT` / `PERCENT_OF_LIST` only, has no
E-125 enum, no `ssp_entry.quantity_unit` column (C1b's migration 0056), no `products.series_product_ids` and no
`books.entry_errors(series_products=)`. The bridge in `ssp_declarations` / `ssp_values` therefore (a) validates the
full E-49 / E-125 vocabularies as literals, (b) resolves the series predicate with the same query as C1b's
`series_product_ids` and prefers C1b's function once the module carries it, (c) reads the book's stored units only when
the column exists (today `{}`), and (d) sends `quantity_unit` to the API only when API-S-SspEntry has the member. A
`PER_INCREMENT` row therefore passes validation today and would be refused by the API at commit (enum), which is the
intended fail-closed state until C1b lands; the `PER_INCREMENT` / `INCREMENTS` round-trip test is owed at the C1b merge
(fixtures for `SERVICE_UNITS` / `INCREMENTS` entries, as the readiness row lists). C1b's claim that "the importer path
already carries the member" was verified by test: the importer reaches `upsert_ssp_entries` and would therefore inherit
C1b's guard at *apply* (a `Problem`, upload INVALID with `IMPORT_PROCESSING_FAILED`-class failure), not as a row-located
validation finding — which is what the readiness row requires and what this lane adds; the two importer files are
byte-identical between main and 053813f.
