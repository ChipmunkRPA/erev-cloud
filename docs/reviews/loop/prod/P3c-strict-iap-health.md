Lane record for platform lane P3c on `sprint/l12` (worktree `~/dev/erev-wt/l12`, base main 43bdaf2, which contains the P3b merge c7dab27 and the D-95 documents). Files-only lane: no database, no server, no Docker, no cloud call, no live third-party call. Input: the supervisor's brief (Codex inbox 1910 "P3 strict-IAP health coverage") and the design contract in `PRODUCTION-P3B-FOLLOWUP-c53b122.md` §"Concrete supported replacement contract" (exact-URL audience, target-service-account signing scope, API-backend-only IAP permission, no redirects, TLS validation, status 200 + JSON `status=ok`, no token logs, missing-execution alerting, `check_passed` on `cloud_run_revision` with the check id). Nothing here weakens IAP; no login page is ever accepted as health.

Official semantics consulted (documentation reads only): IAP "Programmatic authentication" (service-account self-signed JWT: `iss` = `sub` = the account, `aud` = the exact protected URL or a path wildcard, `exp` within 3600 s of `iat`, `Authorization: Bearer`; signing via the IAM Credentials API or a key file; "service accounts can still achieve programmatic access by using self-signed JSON Web Tokens" although the Google-managed OAuth client permits no OAuth programmatic access); Cloud Monitoring "Create synthetic monitors" (Node.js only, entry point `SyntheticFunction`, `UptimeCheckConfig.syntheticMonitor.cloudFunctionV2`, alerting on `monitoring.googleapis.com/uptime_check/check_passed` with `resource.type = cloud_run_revision` and `metric.labels.check_id`, missing executions = absent time series, APIs: Monitoring, Cloud Functions, Cloud Run Admin, Logging, Cloud Build, Artifact Registry, Pub/Sub); `@google-cloud/synthetics-sdk-api` README (`runSyntheticHandler`, a thrown error is a failed check); npm metadata for the exact pins (`@google-cloud/synthetics-sdk-api` 0.7.0, `@google-cloud/functions-framework` 5.0.5); the provider schema of `hashicorp/google 6.50.0` (`google_cloudfunctions2_function` build/service config, uptime `synthetic_monitor.cloud_function_v2.name`, `google_service_account_iam_member`, `google_iap_web_backend_service_iam_member`, `google_storage_bucket_object.source`).

## What was built

**Mode selection** (`main.tf` locals): `iap_strict = enable_iap && !iap_healthz_exemption`; `synthetic_enabled = iap_strict && iap_synthetic_health` (new variable, default true); `tcp_fallback = iap_strict && !iap_synthetic_health`. Exactly one external check exists in every one of the 16 modes: the HTTPS `/api/v1/healthz` check while the path is publicly invocable, the synthetic probe in strict mode, or the TCP 443 fallback. The plain `uptime_url` alert is not created in synthetic mode (`count`), and `local.uptime_check_id` is `try(coalesce(...), null)` so the synthetic mode never fails `coalesce`.

**Runner** (`synthetic/iap-healthz/`): `probe.js` is a pure module (no Google SDK, injected `fetch` and clock). `configFromEnv` accepts only an `https` URL with the bare `/api/v1/healthz` path and a TTL ≤ 3600. `runProbe` obtains the workload access token from the metadata server, calls IAM Credentials `signJwt` for the signer with claims `{iss, sub, aud: exact target URL, iat, exp}`, then `GET`s the target with `redirect: 'manual'`, default certificate verification and `AbortSignal.timeout`. Success only on status 200 with `application/json` and `body.status === "ok"`. Failure classes: `transport` (timeout; TLS codes such as `CERT_HAS_EXPIRED`, `ERR_TLS_CERT_ALTNAME_INVALID`; DNS; connection), `iap-challenge` (any 3xx, location reduced to its origin), `auth` (401/403, naming expiry when the JWT's `exp` has passed), `backend` (other statuses), `body` (200 without the health body), `signing` (metadata or `signJwt` failure; the target is then never called). Every message passes `redact()` (JWT-shaped strings and `Bearer …` values). `index.js` wires `runProbe` into `runSyntheticHandler` under `SyntheticFunction` and logs one credential-free structured line. `package.json` pins `@google-cloud/functions-framework` 5.0.5 and `@google-cloud/synthetics-sdk-api` 0.7.0 exactly.

**README**: the earlier statement that no authenticated probe exists under the Google-managed client is corrected (the self-signed JWT exception), the invocation table's strict-mode row names the synthetic probe with the TCP fallback, and a new section "Strict-IAP health probe (synthetic monitor)" states exactly what each runner result proves and does not prove (readiness and the end-user sign-in flow stay with the Cloud Run probes, SLO-01 and manual QA), the IAM footprint, both alerts and the staging verification items.

## P3d follow-up (Codex retest of 802c87b, PRODUCTION-P3C-IAP-PROBE-RETEST-802c87b.md; merged main e33b827)

Codex accepted the default design (mocks 16/16 on Node v25.9.0, policy tests 5/5, one external check per mode) and raised three residuals, corrected here on `sprint/l12` after `git merge --ff-only main`:

- **P3c-R1, alert timing.** The failure alert counted false samples in a fixed 300 s window and the absence duration was a fixed 600 s, while `iap_probe_period` allows 60, 300, 600 and 900 s: a regular series at 600 or 900 s never placed two failures in the window, and a healthy 900 s spacing exceeded the 600 s absence. Both windows now derive from the period: `iap_probe_failure_window = 2p + 60` s (180, 660, 1260, 1860) so `count_false > 1` means at least two failed results within the alignment window at any period (consecutive or not; corrected wording, P3e), and `iap_probe_absence_duration = max(600, 2p)` s (600, 600, 1200, 1800) so a healthy series never trips it; the absence aggregation aligns on the period. `test_iap_probe_alert_windows_follow_period` recomputes both for every supported value (two executions fit the window; the absence exceeds one healthy gap and holds two; multiples of 60 s; under the 23.5 h ceiling) and pins the formulas and the variable's value set. No exact live alert time is claimed (alignment and ingestion shift it).
- **P3c-R2, absence semantics.** Google ("Create metric-absence alerting policies"): a metric-absence condition "requires at least one successful measurement" and "won't be met when the subsystem that writes metric data has never written a data point". The `main.tf` comment and the alert documentation no longer claim to detect a function that failed to deploy; `iap_probe_missing` detects a monitor that stops after it has executed. The never-started case is deployment evidence, not a metric: new variable `iap_probe_first_execution` (`{ execution_id, observed_at }` or null, RFC 3339 validated with `try()`), recorded by the operator after the first synthetic execution and echoed by `output iap_probe.bootstrap` (`first_execution_recorded`, `never_started_detection`); the README staging checklist requires the first execution, its first `check_passed` data point and the recorded evidence before the probe counts as monitored. No automated never-started detector is provided and the README says why (no "expected first point" condition; a smoke execution needs an authenticated call the loop never makes). Failed executions still write false samples, so a failing monitor is a `iap_probe_failed` incident, not an absence.
- **P3c-R3, body read.** `await response.text()` sat outside the transport `catch`, so a timeout or reset after the 200 headers threw out of `runProbe` and `index.js` could not emit its structured result. The body read is now inside transport handling and returns one classified, redacted record (`transport`, "body read failed after status 200: timeout" / "connection: ECONNRESET"). Three mocked cases added (body timeout, body reset, token-carrying body error redacted): `probe.test.mjs` 19/19 on the local Node v25.9.0; the deploy runtime is `nodejs22`, which was not executed and stays a staging item. Fail-first against the committed 802c87b/e33b827 artifacts: the three new runner cases fail (`.run/p3c/fail-first-p3d-node.log`, 16 pass / 3 fail) and `test_iap_probe_monitor_contract`, `test_iap_probe_alert_windows_follow_period`, `test_iap_probe_runner_mocked_cases` fail (`.run/p3c/fail-first-p3d-pytest.log`, 3 failed / 11 passed). After the change, every check inside an exit-code-gated chain: `probe.test.mjs` 19/19, architecture + deploy + Makefile tests 135 passed (`.run/p3c/arch-tests-5.log`), `make lint` rc 0 (`.run/p3c/make-lint-3.log`), `terraform fmt -check` 0, `validate` Success.

- **P3c-IF1 (Codex `PRODUCTION-P3C-TF-INTERFACE-171d79a.md`, 14 synthetic cases with P1's wrapper: 13 pass / 1 fail).** The inherited test-only `EREV_TF_VALIDATE_ROOT` could point `ROOT` at a foreign module B while `EXEC_ROOT`, the report and `source_binding` identified captured context A. `scripts/tf_validate.sh` now derives the module root from the execution context: under `EREV_GATE_CONTEXT` the module is the context's own tree (`pwd -P` of the context), and an override that does not resolve to it is refused before any terraform call with `FAIL`, `failures[] {stage: source, exit_code: 1}`, result `foreign-module-root`, `module_root_override` naming the rejected path, `module_root_rejected: true`, stages all `skipped` and the identity still that of the context (a well-formed DG-MK-00g record, so the wrapper fails closed on exit_code 1). Without the wrapper the override is honoured only under `EREV_ENV=test` (the isolated tests) and refused otherwise with the same record. Tests: `test_tf_validate_rejects_foreign_module_root_under_gate_context` (foreign tree marked `FOREIGN_SOURCE_B`; no stub call recorded; report shape), `test_tf_validate_accepts_matching_override_under_gate_context` (override equal to the context validates normally), `test_tf_validate_override_is_test_only_without_gate_context` (`EREV_ENV=dev` refused, `EREV_ENV=test` honoured); `test_tf_validate_rules` pins the tokens and that the rejection precedes the first terraform invocation in the script.

- **P3e (wording, Codex retest of 894080a / 86b274d: P3d and IF1 accepted).** "Two consecutive failures" overstated the condition: `count_false > 1` over a `2p + 60` s window fires on at least two failed results within the window, consecutive or not (F,T,F fires too), and DPL-37 / the SLO table / DEP-4 / REQ-OPS-002 require no consecutiveness. Corrected in the `main.tf` comment and alert display name, the README and this record; the test comments say the same. No resource or test assertion changed.

## Residual limits
