## 0. Summary of decisions

### 0.1 Governing rule (Codex continuation map, point 5) and scope (point 1)

"Bound rerun/explain must rebuild from captured pre-aggregation inputs or proven immutable references, with no live fallback or cached-output substitute." Every treatment below is one of those two: retained PRE-AGGREGATION inputs (rows / ids / values the builder consumed BEFORE it aggregated — never an aggregate, never an output) or a proven immutable reference (a row id whose row cannot change, a child of a bound version). Scope = the incomplete families of all TEN adapters + all SEVEN `open` builders = 17 incomplete builders; `api_client_inventory`'s real retained-input rebuild (frps3b) is preserved as the eighteenth, already complete.

Every incomplete input family is closed by one of three treatments, all inside the EXISTING binding form (`binding_version` 1; §3):

- **BIND-IDS (rebuild from bound row ids):** the live build records the ids of the immutable rows it consumed (`members.<kind>`); a bound run re-reads exactly those rows (`tie_outs.bound_member_where`) and recomputes — the waterfall's `members.subledger_line` precedent (`revenue_waterfall.py:359–362`). Used for every subledger-line and journal-line population.
- **RETAIN (retained input evidence):** the live build records the consumed VALUES (`evidence.<kind>` / `labels.<kind>`); a bound run feeds them to the same logic — the `api_client_inventory` precedent (`builders/api_client_inventory.py` `_live_inputs` / `_from_evidence`; `tie_outs.record_evidence` / `bound_evidence`). Used for mutable configuration and labels and for populations that are re-generated rather than appended (migration reconciliation rows).
- **CHILD (no capture needed):** rows that are immutable children of already-bound ids (obligation versions, predecessor obligation versions, balances, traces, T-SL-12 event sets, contract events, cause-event ids) — rebuilt by the bound id; stated, not captured.

## 2. RETAIN vs REBUILD, per family — the decision and the reason

### 2.1 Family 1 — consumed configuration (all TEN adapters) → RETAIN

- **What is retained** (`evidence.configuration`, recorded once per live build by the helpers themselves): `entities` = the `legal_entity` rows consumed (`id, code, calendar_id, functional_currency, time_zone`), `periods` = per consumed `calendar_id` the period rows (`id, period_key, name, fiscal_year, period_no, quarter_no, start_date, end_date`), `book_code`. Entity codes used as row labels are ALSO recorded as `labels.entity_code` (per entity id) through `label_for` so a bound row query never joins `legal_entity` live.
- **How a bound run reads:** `tie_outs.entities` / `calendars` / `book_of` return the evidence when `params.binding` is set (no query; missing evidence → `INCOMPLETE_BINDING` by name — never today's rows); the pure range functions run over the retained calendars. `views._entities` (legacy JE) reads the same evidence.
- **Why RETAIN, not BIND-IDS:** the rows are MUTATED in place (a calendar reassignment or a period edit changes the same row id), so an id binding would re-read changed values. Size is small (entities: units to tens; periods: ≤ a few hundred per calendar).
- **Effect:** `_CONFIG_OPEN` is removed from every adapter's `open` list; the docs' "consumed-configuration completeness is NOT claimed" sentence (S15-R-24; 04 T-RPT-02; DG-AK-41) becomes "bound as retained configuration evidence".

### 2.2 Families 2 and 3 — subledger-line memberships; product labels → BIND-IDS; RETAIN

- **BIND-IDS:** the four balance-family builders and `disaggregation` record the line ids they consumed as `members.subledger_line` (the waterfall's precedent) and apply `bound_member_where` under a binding, re-reading the amounts / kinds / dimensions from the rows (the REBUILD). `revenue_from_opening_liability` sums today without selecting ids: its live build gains one id query with the SAME predicates (or `array_agg(id)` in the grouped select) to record the members; the sum query is unchanged; under a binding the sum query carries `bound_member_where` instead of the live predicates. `contract_cost_rollforward`'s `period_end_date <= max(range_end)` and the NETTING exclusion stay as they are on the live path; under a binding the membership replaces them (the recorded ids already satisfied them).
- **Why BIND-IDS, not RETAIN:** a subledger line is immutable and server-stamped (DB-08); re-reading by id is a true rebuild of the amounts through the same aggregation, and the ids are what an explanation must name as contributors. Retaining amounts would be output retention (rejected in frps3b, Codex 2225).
- **RETAIN (labels):** `disaggregation` binds `product_family` and `product_revenue_category` per `product_id` through `tie_outs.label_for` (as `rpo.py:488` and the waterfall do); a bound run never joins `product` live. **Family 2b:** `tie_outs.balances_at` binds `customer_name` per `customer_id` through `label_for` (the customer id is selected alongside the name; under a binding the value is the retained label, never the live join) for `contract_balances`, `contract_balance_rollforward` and `revenue_from_opening_liability`.
- **Divergence:** a bound line id that no longer exists (or a changed label) cannot be "completed from today's rows": a missing bound row makes the rebuilt figures differ → CTL-029 records the mismatch (§4); a missing label refuses by name.
- **Size (measurement point, §3.3):** the line count of a range run can be thousands; the waterfall already stores such sets. Slice 3c-2 records `summary.members` for every run so the DB stage can measure the actual maximum before any storage decision.

### 2.3 Family 4 — C4's reference-to-period association → RETAIN the association map

- **What is retained** (`evidence.reference_periods`): the exact output of `_references` — for each `(entity_id, period_id)` in the run's range the set of referenced `contract_version_id`s (string keys `"<entity_id>:<period_id>"` → sorted ids). Small: one entry per (entity, period), a few ids each.
- **How a bound run reads:** `_references` returns the retained map (no `subledger_line` read); `_selected_versions` then applies the SAME per-(group, period) latest rule over the bound eligibility (`bound_version_where`, frps3b) — so both what Codex distinguished are fixed: eligibility by bound ids, association by the retained map; `period_ids` per version are therefore identical, hence the same trace nodes are read and the same `check_identity` runs.
- **Why RETAIN the map, not BIND line ids:** the lines contribute nothing but the association (distinct triples); binding thousands of line ids to reproduce a map of a few dozen entries is the heavier and less legible choice. The map IS the consumed input — Codex map point 3, verbatim: C4 "requires the reference-to-entity/period/version ASSOCIATION, not merely the union of eligible version IDs"; the union of ids is `versions` (eligibility); the association is `evidence.reference_periods`.
- **`params.known_at` vs the effective cutoff (Codex -0020 (b)):** `_references` and `_encoded_contracts` read at `params.known_at` (the run's stored value, copied verbatim to a rerun — on a record-basis original it can be EARLIER than the effective cutoff `cutoff_for` applied to version selection); after 3c-3 neither read happens under a binding (map retained; `members.contract` bound), so the distinction is documented, not relied upon. The live path keeps both instants as they are.

### 2.4 Family 5 — the history-family exports and latest status → CHILD (+ family 1) → become `adapter`

- `legacy_contract_history_export`, `legacy_latest_contract_export` and `latest_contract_status` reuse `contract_history.population` / `latest_where` / `date_range`, which ALREADY apply `cutoff_for` and `bound_version_where` (`contract_history.py:139–194`). What they lack is the RECORDING on a live build (`tie_outs.record_consumed_versions` is called by `contract_history.build` at `:272`, not by these three) and the configuration evidence (`default_dates`).
- **Decision:** call `record_consumed_versions(params, book_code, ids)` for the population's version ids in the three builders (or move the call into `population`); the predecessor obligation rows (`previous_versions`, by `previous_obligation_version_id`) and `_balances` (`contract_version_balance` by version id) are CHILD of the bound versions — no capture. **Preservation requirement (Codex map point 4):** the predecessor rows for legacy conversions are preserved — a bound run reads exactly the predecessor obligation versions the original's rows named, by id. With family 1 they declare nothing open → strategy `adapter` (rerun = same-source rebuild; legacy runs refused by name as for every adapter — a behaviour change for their legacy runs, stated in §4).

### 2.5 Family 6 — `legacy_je_summary` → BIND-IDS + RETAIN

- **BIND-IDS:** `views._consolidated` selects line rows: record their ids as `members.subledger_line`; under a binding `bound_member_where` replaces the window / book / entity / `recorded_at` predicates (the recorded ids satisfied them). The GROSS / DELTA arithmetic (`signs`, `_sides`, `_by_account`) is the rebuild.
- **RETAIN:** `evidence.legacy_books` = `{entity_id: is_enabled}` as read by `_require_legacy_book` (a later disablement cannot move a rerun — flagged §7); `labels.gl_account_code` per `gl_account_id` (account codes are mutable configuration; the view groups by account code).
- **Why:** lines immutable → ids; enablement and account labels mutate in place → values.
- **Effect:** strategy `open` → `adapter`; `_LEGACY_JE_OPEN` removed.

### 2.6 Family 7 — `je_population` → BIND-IDS (+ CHILD histories) + RETAIN labels

- **BIND-IDS:** `members.journal_line` = the population's line ids (replacing `created_at <= known_at` + scope predicates under a binding); `members.journal_run` = the runs whose totals the "independent total side" (`tie_out(rows, run_debits)`) compares against (the same kind the waterfall binds).

The design states this as a property relied upon (append-only + server stamps), reviewable (open question §9.3). **Preservation requirements (Codex map point 4):** the independent JE run totals (the total side compared by `tie_out`) are read from the BOUND `members.journal_run`; the ORDERED state / approval history (`chain_seq`, `created_at` order) is rebuilt in the same order from the same append-only rows.
- **RETAIN labels:** `labels.gl_account_code` (and `gl_account` name if displayed), `labels.display_name` per actor id (approvers, creators) — mutable.
- **Effect:** `open` → `adapter`; `_JE_POPULATION_OPEN` removed; the DATASET_FREEZE / `state_as_of` refusals unchanged.

### 2.7 Family 8 — `out_of_period_register` → BIND-IDS (+ CHILD) + RETAIN labels

- **BIND-IDS:** `members.subledger_line` = the register's line population (replacing the scope predicates under a binding); `versions` = the `contract_version` ids whose `cause_event_ids` supplied the per-book cause PROOF (`_cause_event_counts` by computation id) — recorded through `record_consumed_versions` so the proof is re-read from the same versions.
- **CHILD:** `subledger_posting`, `contract_computation` (trigger, created_at, creator) via the line's posting id; `contract_event` + `approval_request.request_no` via the line's event id; the ordered T-SL-12 `subledger_line_event` sets by line id — all immutable children of the bound lines. **Preservation requirements (Codex map point 4):** the missing-proof vs proved-zero semantics (`attribution`, `attribution_missing`: `cause_event_count == 0` with a non-event trigger is a proved zero; anything else without a T-SL-12 set is missing lineage and refuses) run unchanged on the rebuilt read, and the EVENT ORDER (`subledger_line_event.ordinal`) is the same ordered read of the same rows.
- **RETAIN labels:** `labels.display_name` per actor id (`_actor`).
- **Effect:** `open` → `adapter`; `_OOP_OPEN` removed.

### 2.8 Family 9 — `migration_reconciliation` → RETAIN

- **What is retained** (`evidence.migration_reconciliation`): the `migration_batch` row fields the report reads (id, migration_no, status, cutover / promotion fields as used by `_batch` / `_kpis`), the `migration_reconciliation_line` rows consumed (all columns the `Line` model reads: keys, measures, legacy / engine values, tolerance, exception item ids) and the `exception_no` map. Size: one row per (contract, obligation key, measure) of the batch — hundreds to low thousands; a Codex decision point if the DB stage measures more (§3.3).
- **How a bound run reads:** `build_with(rows_reader=, batch_reader=, exception_reader=)` (`migration_reconciliation.py:244–263`) already takes injectable readers: under a binding the three readers are evidence-fed; the live path is unchanged and records what the repository readers returned.
- **Why RETAIN:** reconciliation rows are RE-GENERATED by a later reconciliation of the same batch (same batch id, new rows) and the batch row mutates (status) — ids would re-read changed rows; retaining the consumed values is the only faithful same-source rebuild. Exception numbers are immutable but their visibility is not.
- **Effect:** `open` → `retained_inputs` (the api_client_inventory strategy), not `adapter`: nothing is version-bound.

## 4. Rerun / explain semantics and CTL-029

- **Governing rule (§0.1):** a bound rerun / explanation rebuilds from captured PRE-AGGREGATION inputs or proven immutable references — no live fallback, no cached-output substitute; `revenue_from_opening_liability` is the test case: its live aggregate (`func.sum`) is NOT retained; the line ids are, and the bound run re-aggregates them.
- **Unchanged framework:** `run_report` always rebuilds through the builder (frps3b Codex 2225); a bound run's helpers return bound ids / retained values instead of querying; `explain_cell` resolves against the same binding. A run whose `sources.open` is empty after its slice is a COMPLETE same-source binding (`sources.complete` true, 3c-9); until then `open` names exactly what a rerun still reads live.
- **When a same-source rebuild differs:** CTL-029 records `output_sha256_equal` / `control_totals_equal` false (control FAIL, job SUCCEEDED — existing behaviour; frps3b DB case (e′)). With a complete binding the causes are enumerable: (i) a calculation change (the registered builder / release changed — the intended detection), (ii) a bound row absent or changed in place (a deleted line, a re-generated reconciliation row that was NOT retained — impossible by design for the retained families, detectable for id-bound ones because the rebuilt figures differ), (iii) an incomplete binding — refused by name BEFORE any figure is produced (`INCOMPLETE_BINDING`, `BINDING_INCOMPATIBLE`), never a silent live fallback. Option for Codex: a `BOUND_ROW_MISSING` named refusal when `bound_member_where` returns fewer rows than bound ids (turning (ii) from a detected mismatch into a refusal by name) — proposed, not decided.
- **Legacy runs of the six ex-`open` builders:** once a builder is `adapter`, its SUCCEEDED runs created before its slice (no binding) are `legacy_unbound` and REFUSE rerun / explanation by name (they are no longer "new live evaluations"); their FAILED originals still rerun as new evaluations. The change is stated in each slice's docs (04 §16.9, SCREENS_B RV-03 copy).
- **CTL-029 is not source-identity proof** (frps3b): equality of hash / totals says the rebuild reproduced the output; the binding's identity of ids / values is what says it was the same source.

## 5. C4: eligibility vs reference-to-period; `params.known_at` vs the effective cutoff

Restated as the contract for slice 3c-3 (Codex -0020 (b); continuation map point 3: the ASSOCIATION, not merely the union of eligible version ids): (1) `versions` (bound ids) restrict which versions are ELIGIBLE; (2) `evidence.reference_periods` fixes which eligible version is read for which (entity, period) — the ASSOCIATION; (3) `members.contract` fixes the historical identities (frps3b); (4) the effective version cutoff is `cutoff_for` (bound instant under a binding; on a record-basis original the later of `known_at` and the transaction time; on an explicit historical read the supplied `known_at` — the shared READ-1 rule adopted at 28c01bbf); (5) `params.known_at` (copied verbatim to a rerun) bounded the live `_references` and `_encoded_contracts` reads on the ORIGINAL build only — a bound run performs neither read. The record-basis live path keeps (4) ≠ (5) exactly as today; no widening of historical selection.

### 10.4 D4 — the named missing-input refusal; authorization and scope integrity
