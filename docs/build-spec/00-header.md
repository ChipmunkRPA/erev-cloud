## 1. Purpose and how items are ticked

This document orders the work of the Ralph loop that builds eRev Cloud 1.0 (`docs/00-GOAL.md`). The phase sections follow this header and the generated phase index (§8) in the order of PHASES §3. Every phase ends with a checkpoint item `GATE-<code>` (§6); the release phase REL ends the items (§7). Three appendices follow the items: A, the table of contents of every item id and title; B, the author notes and the author decisions that items cite; C, the coverage waivers.

The loop reads this header, the current item and the next item each iteration (PROMPT.md). It reads every other document only where an item cites it, by grep and offset reads.

An item is **done** only when all of the following hold:

1. Its acceptance criteria are met and every named test passes.
2. The dev-guide §10.4 checklist DG-DONE-01 to DG-DONE-12 is satisfied.
3. Every gate that §3 requires for the item's kinds is green, in a run made after the item's last change.
4. `PROGRESS.md` ticks it in the dev-guide §10.5 format, extended by BS-D-23:

   ```markdown
   - [x] <ITEM-ID> <item title>
     - Evidence: make ci OK (backend 612 passed, 0 failed, 3 skipped; vitest 214 passed; build OK); make test-pg OK (388 passed)
     - Tests: backend/tests/domain/contracts/test_activation.py::test_ctl_004_activation_gate_blocks_missing_document (CTL-004)
     - REQs completed: REQ-CON-005
     - Commit: <short sha>
     - Spec questions: SPEC-Q-7 (04 T-CON-06 vs PRD SM-04; followed 04)
   ```

   Counts come from `.run/reports/<target>/report.json` (DG-GATE-04), never from memory.
5. It is committed with `PROGRESS.md` per DG-GIT-01 to DG-GIT-03.

Order: the loop finishes an item under **In flight** first; otherwise it takes the first unticked item in document order. It may complete several small items in one iteration, ticking and committing each separately, and never ends an iteration with `make ci` red (PROMPT.md).

A release-1.0 requirement counts for G1 when its completing item is ticked and every acceptance hint it carries has closed as PHASES §15 states.

Rules:

1. **Reviews.** The reports in `docs/reviews/` record why the documents changed. The amended document governs; an objection file never governs (`docs/01-DECISIONS.md` §0).
2. **Conflicts.** The loop follows the higher-precedence document, records `SPEC-Q-<n>` with both references and the choice made (DG-DONE-12), and continues. It never edits a supervisor document (DG-GIT-05) or an expected value in the answer keys, `docs/legacy/golden/` or `deviations.json`. When it believes an expected value is wrong, it records the spec question and leaves the item unticked.
3. **Freeze (D-77).** The design documents and the answer-key corpus are frozen. Open-question ids are cited as `<document>:<id>` (D-76).

## 4. Cross-cutting rules for every item

- **XR-01 Migrations.**
  - One handwritten Alembic revision per item that changes the schema, created with `make revision MSG=<summary> ITEM=<item id>`. Its docstring names the item and the 04 ids created (DG-MIG-02, DG-MIG-03). Autogenerate is never used.
  - The revision is self-contained: tables with keys and indexes, composite foreign keys (NC-06), the RLS template (04 §1.4), the IM class and grants through `apply_class` (04 §1.5, §14.2), transition triggers (DB-03), monthly partitions (DG-MIG-10), and enum types created with their rev 1.2 values (04 §18 rules 5 and 6; DG-MIG-06). Objects appear in 04 §18 dependency order; a foreign key to a later table is added by the later table's revision.
  - `downgrade()` removes exactly what `upgrade()` created (DG-MIG-04). `test_single_head`, `test_upgrade_downgrade_upgrade` and `test_lint_after_upgrade` pass (DG-MIG-05).
  - Every new tenant table has a `ROW_BUILDERS` entry and joins the isolation suite (DG-TST-16, DG-TST-20). Every DB invariant it enforces has `test_db_<nn>_<slug>` pass and violation tests (DG-TST-23).
  - An index of a tenant table has a key the row-level-security policy can use (04 NC-20; DG-KRN-DB-10; rev 1.112): the columns compared with leakproof operators stand in front, an enumeration or a `numeric` column last, a status or a kind a read asks for is the predicate of a partial index. `test_nc_20_every_index_of_a_table_with_a_policy_can_be_used_under_it` passes, and a read that depends on the index has a plan test read as `erev_app`.
  - Migrations seed only global catalogues (DG-MIG-07). A table named in the 04 §14.3 provisioning seed extends `tenant.provision` in the same item (BS-D-12).
- **XR-02 Command pattern.**
  - Every state-changing operation, from any channel, is a handler that runs DG-CMD-01 to DG-CMD-08 in order: authorize, load and lock, validate (collect every finding), compute (at most one engine call per group), persist append-only, audit (one event per affected object), emit (rows only), commit through `run_command`.
  - Command routes use `command(...)`. They require `Idempotency-Key`; a missing key returns 422 `validation-failed` with `rule_id` `API-C-04` (DG-KRN-IDEM-01). Mutable resources require `If-Match` (API-C-08).
  - Decision and fact-capture commands follow DG-CMD-09 and DG-CMD-10. Routes hold no domain logic (DG-CMD-11). Queries never write and apply `as_of` and `known_at` (DG-CMD-13; API-C-10).
- **XR-03 Money.**
  - `Decimal` end to end; money is a string on the wire with an explicit currency, and a JSON number for money returns 422 (REQ-PLT-031). Stored types are `erev.money`, `erev.exact` and `erev.fx_rate` (D-11).
  - The engine holds exact values as `Fraction` and posted values as integer minor units, with `FloatOperation` trapped (DG-ENG-03). Rounding happens only through `erev_engine.money` (ALG-01; DG-ARC-06). Minor units come only from `ISO_4217`.
  - The frontend never converts a money string to a number, and totals come from the API (DG-FE-08).
- **XR-04 Registry.**
  - Policy and platform values are read only through `erev_api.registry.resolve` (dev-guide §5.15) and, in the engine, through `ctx.policies.value` (ENGINE_SPEC CV-17). Keys and option literals are exactly those of POLICIES §1 and T-PLT-31 (D-13a).
  - `backend/erev_api/registry/policies.py` is generated by `make registry-seed` and never edited by hand (DG-LAY-07). No other code holds a policy default literal.
  - Behaviour switches are policy values, never tenant ids, environment variables or legacy flags (DG-ENG-09). Configuration changes follow the SM-04 lifecycle under approval (REQ-POL-003).
- **XR-05 Explainability.** Every engine output value has a trace node with a formula id, and `reevaluate` reproduces it (DG-ENG-04; PROP:P14). Parity measure names equal column names (DG-PAR-05). Every persisted computed measure is served by `/explain` (API-R-49), and every computed figure on screen sits in `<ExplainTrigger figureRef>` (DG-FE-15; REQ-UX-005). A figure without a trace path is a defect.
- **XR-06 Identifiers verbatim.** Enumeration literals, permission codes, problem slugs, and finding and exception codes are written exactly as 04 §3, T-PLT-11, §15.2 and §15.4; route paths and screen ids exactly as SCREENS §0.4; copy exactly as SCREENS, SCREENS_B and PRD §5.5; `data-testid` values per SCREENS SCR-TID-02 to SCR-TID-04 (D-73; DG-READ-03). Where another document spells a literal differently, the owner's spelling is used and a spec question is recorded. The drift tests DG-ARC-09 and DG-ARC-13 stay green.
- **XR-07 Tests and markers.**
  - Test layout follows DG-TST-01 to DG-TST-05; engine tests request no database fixture (DG-TST-18).
  - `parity`, `answer_key`, `property`, `pg` and `perf` are applied only through module `pytestmark` in their directories (DG-TST-07). `@pytest.mark.control("CTL-nnn")` marks a test of the control: the tests tagged for a control exercise its failure path — at least one of them — and a tagged test may assert a clause of the control's row operating (DG-TST-06, dev-guide rev 1.252).
  - `skip`, `xfail` and `skipif` are forbidden in parity, answer-key, property, pg and control tests (DG-TST-09). Tests over 10 s carry `slow` (DG-TST-08). A failing Hypothesis example is pinned with `@example` before the fix (DG-PROP-02).
  - API tests use `committed_db` and fresh tenants; factories create data through commands (DG-TST-13, DG-TST-16). No network (DG-TST-15); frozen clock (DG-TST-14).
  - Named tests are binding for evidence (BS-D-22). CHK rows have `test_chk_<nnn>_<slug>` (DG-ENG-11), and `TC-` hints have `test_tc_<doc>_<nn>_<slug>` (BS-D-21).
  - Never weaken, skip or delete a test, and never edit an expected value, to make a gate pass (PROMPT.md).
- **XR-08 Tenancy, scope and personal data.** Runtime connections use `erev_app` behind the role guard (DG-ENV-12), with the tenant set by `SET LOCAL` per transaction (D-42). Handlers check entity scope with `require_for_entity`, and out-of-scope ids return 404 (DG-CMD-01; REQ-PLT-012). Export, posting and conversion commands call `ensure_production` once sandboxes exist (REQ-PLT-022). Logs carry no personal data (DG-LOG-03, DG-LOG-07), and secrets are read only through `SecretStore` (DG-ENV-17).
- **XR-09 Seed extension.**
  - From the first WEB seed item onward, an item that adds user-visible data, or a capability that a seeded tenant uses, extends the `erev seed demo` builders in `backend/erev_api/domain/demo/`. Screens then render PRD §2 content (REQ-DEMO-006).
  - Builders run domain commands as persona users, with maker and checker as different personas (WLD-R-02); direct inserts are allowed only for global catalogues. Output is deterministic with seed `20260912` (WLD-R-01; REQ-DEMO-007).
  - The seed refuses non-demo tenants and users outside `demo.erev` (WLD-R-04), takes passwords only from `EREV_DEMO_PASSWORD` (DG-RUN-32) and never touches `perf-volume` (DG-PERF-06).
- **XR-10 User interface.**
  - A screen item is complete when every region, binding, state, copy string and test hook of its screen ids exists and `screens.spec.ts` captures them (SCREENS SCR-IA-00).
  - States follow SCREENS SCR-ST-01 to SCR-ST-12 (DG-FE-14), permission gating SCR-PERM-01 to SCR-PERM-07, URL parameters SCREENS §0.5, and chips SCREENS §0.8 and SCREENS_B §0.4.

  - Route objects carry `id` and `handle` per SCREENS SCR-IA-06 and DG-FE-02. Reads pass `as_of` for the context period (BR-UX-02); commands go through `useCommand` (DG-FE-05); dates go through the format module (DG-FE-20).
  - Captures are named per BS-D-09. After `make e2e` the loop reads both themes of each capture it added or changed, records a finding in `PROGRESS.md` before fixing it, and fixes deviations before ticking (PROMPT.md).
- **XR-11 AI.** AI follows DG-AI-01 to DG-AI-09. `FakeProvider` is the only provider under `test`, `e2e` and perf runs. Anthropic SDK code lives only in `backend/erev_api/adapters/ai/anthropic.py`, is written after reading the `claude-api` skill documentation, and is tested only against a mocked SDK client. AI output is a proposal; acceptance is an audited human command (D-46; CTL-045).
- **XR-12 Fail closed.**
  - When an item consumes a signal that a later item produces (unacknowledged journal batches before export exists, judgement review status before close gates, interface control totals before imports), the missing producer yields the conservative outcome: gate blocked, not certified, not auto-approved, not posted. A test proves it, and the producing item re-runs that test with the real signal.

- **XR-14 No placeholder UI.** No placeholder pages, "coming soon" copy, TODO stubs or disabled features presented as built. The rail, the settings index, route tab bars and the command palette list only built routes (SCREENS SCR-IA-01 to SCR-IA-03). Landing routes follow BS-D-08.
- **XR-15 API surface.** Routes follow dev-guide §6.4 and 04 §15, declare their problem responses, and use DG-LST lists. `docs/api/openapi.json` and `frontend/src/lib/api/schema.d.ts` are regenerated by `make openapi` in the same commit (DG-LAY-07). - **XR-17 Shared machine and git.** The standing constraints of `docs/00-GOAL.md` §5 apply: ports, PID files, no `/tmp` (DG-RUN-30), only the three databases, no database or role administration (DG-FORBID-03), and no network except `make setup` (DG-MK-00f). - **XR-18 Spec questions (D-77).** Gaps and conflicts go under **Spec questions** in `PROGRESS.md` as `SPEC-Q-<n>` with both references and the interpretation taken, and the loop continues. - **XR-20 Engine purity.** `erev_engine` imports only the standard library and performs no database, filesystem, network, clock, randomness or float access (D-10; DG-ENG-01 to DG-ENG-03; DG-ARC-02). ## 6. Checkpoint items `GATE-<code>`

Each phase ends with this item. It verifies and records evidence; a defect found here is fixed in the same item, with its own test.

```markdown
- [ ] **GATE-<code> Phase <code> checkpoint.**
  - **Prerequisites:** every item of phase <code>
  - **Scope:** verification and evidence; fixes only for defects this checkpoint finds
  - **Acceptance:**
    - Exit criteria: every exit criterion of PHASES §1 row <code> holds, each with the evidence named there
    - Membership: every REQ of PHASES §6 for <code>, control of §7, route row and placement of §10, journey of §11 and make target of §13 assigned to <code> is cited by a ticked item, and each REQ is listed under "REQs completed" by exactly one item
    - Gates: the PHASES §4 row GATE-<code> is green on a clean tree (`git status --porcelain` empty) after the last commit
  - **Read:** PHASES §1, §4 and the membership rows for <code>
  - **Gates:** GK-11
```

The tick in `PROGRESS.md` is a checkpoint block:

```markdown
- [x] GATE-<code> Phase <code> checkpoint
  - Evidence: make ci OK (…); make test-pg OK (…); <every PHASES §4 gate of the row with its counts>
  - Membership: REQs <n> of <n>; controls <n> of <n>; route rows <n> of <n>; journeys <n> of <n>; make targets <n> of <n>
  - Spec questions opened in this phase: <SPEC-Q ids or "none">
  - Supervisor verification needed: <entries or "none">
  - Commit: <short sha>
```

Rules:

- **Collapsing evidence.** At the checkpoint, the loop collapses the phase's ticked items in `PROGRESS.md` to one line each (id and commit), which keeps the file under 20 KB (PROMPT.md).
- **No pause.** The checkpoint does not pause the loop (BS-D-14). The loop continues with the next phase, and the supervisor reviews asynchronously.
- **Regressions.** A regression in an earlier phase that the checkpoint finds is fixed before the checkpoint is ticked (DG-GATE-02).
