Rules:

1. Every REQ with release `1.0` is built and ticked in `docs/BUILD_SPEC.md` (G1), whatever its priority. Release decides whether it is built; priority decides order and triage.
2. Within an area, and subject to dependencies, P0 items are built before P1, and P1 before P2.
3. A `later` REQ is not built. Where its description says "Reserve:", the named hook (column, enum value or interface) is present in 1.0 and unused; otherwise nothing of it is built.
4. Every `docs/00-GOAL.md` §2 capability maps to at least one 1.0 REQ (D-04); §7 is the proof.
5. Moving a 1.0 REQ to later, or a later REQ to 1.0, requires a new D-number.

### 6.3 Customer data access for BI (M-PM-06, L-03)

Decision: 1.0 ships **CSV extracts with a JSON manifest** (REQ-RPT-028), both full as of a snapshot and incremental by `known_at`, with versioned dataset schemas. The legacy 71-column dataset is one of those schemas, so BI models built on the legacy SQLite table keep a stable contract (L-03).

- **Parquet:** later P1 (REQ-RPT-029).
- **Read-only SQL views:** single-tenant self-hosted deployments only, later P2 (REQ-RPT-030).
- **Hosted pooled deployments:** never get direct database access. Under D-42 the tenant is set per transaction with `SET LOCAL`, so a customer holding a database session could set another tenant's id; isolation holds only when the application controls the session.

Rationale: CSV satisfies Power BI, Tableau and warehouse loaders without new dependencies or isolation risk.
